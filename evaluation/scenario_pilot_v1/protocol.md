- 작성일: 2026-10-01
- 대상: `CanelE452/github-related-bug-issue-finder`
- 확인한 원격 기준 커밋: `cf9e3e24e0b432fb9f98e30d92d46d5c2b604369`
- 작업 유형: 합의한 검색 평가 계획의 CLI 실행 인계 — Phase 0 → 2 → 3
- 이 문서는 **실험 설계와 실행 계약**이다. 아직 이 문서의 실험을 실행했다는 뜻이 아니다.
- 사실은 `[확인]`과 출처를, 실행 조건·평가 설계는 `[추정·미검증]` 또는 `지시`로 구분한다. 수치 예산은 연구 분야의 표준 합격선이 아니라 이번 파일럿의 운영 상한이다.

## 0. CLI가 먼저 읽을 작업 요약

### GOAL

**사용자가 오픈소스 사용 중 겪은 상황을 설명했을 때, 다음 행동을 판단하는 데 유용한 기존 Issue를 찾을 수 있는지 검증한다. 실패가 문서 미수집·Bug 필터 제외·질의 정보 부족·언어 차이·검색 순위 중 어디에서 발생했는지 분리한다.**

독자는 사용자·프로젝트 팀·담당 교수다. 결과로 다음을 결정한다.

1. 상황 설명 기반 검색을 핵심 기능으로 유지할지.
2. 수집 범위/필터, 입력 보조, 검색 방식 중 무엇을 먼저 수정할지.
3. 검색 개선보다 댓글·해결 근거 정리에 집중할지.

목적은 임베딩이나 Hybrid가 더 좋다는 결론을 만들어내는 것이 아니다. 차이 없음·역효과·데이터 부족도 유효한 결과다.

### 지금 허용된 실행 범위

지시:
- 기존 코드를 읽고, 별도 평가 도구와 테스트를 최소한으로 추가한다.
- 공개 Issue 데이터의 동결 스냅샷을 확보한다.
- OpenCV와 Transformers에서 **12개 개발 사례**를 구성한다.
- 기존 BM25/다국어 임베딩/Hybrid를 변경 없이 비교한다.
- 수집·필터 점검, 상황 설명 검색, 표현/조건 변형, 제한된 무정답 검사를 준비·실행한다.
- 사람 검토가 없더라도 **후보 질의·검색 순위·검토용 자료까지** 만든다.
- 실제 사람이 검토한 질의·관련성 판단이 없으면, 사람 검증 검색 품질 지표를 확정하지 않는다. 이때 상태를 `AWAITING_HUMAN_REVIEW`로 남긴다.
- 사람이 검토한 자료가 이미 있으면 검증 후 이어서 계산한다. 같은 계획을 다시 승인받을 필요는 없다.

### 지금 하지 않을 것

지시:
- 새 모델 학습, 미세조정, Cross-Encoder 추가, 로그 파서, 정규화, 점수 가중치 튜닝을 하지 않는다.
- 검색 결과를 보고 질의를 더 잘 검색되도록 다시 쓰지 않는다.
- LLM(대규모 언어 모델) 요약/자동 해결책 생성/자동 코드 실행을 추가하지 않는다.
- 사용자 화면, 기본 Bug 필터, 기존 수집 한도를 몰래 변경하지 않는다.
- 기존 중복 쌍 평가를 삭제하거나 이 실험으로 덮어쓰지 않는다.
- 웹 검색 실사용 비교는 프로토콜과 기록 양식을 만든다. 사람이 수행하지 않은 시간을 만들어 기록하지 않는다.
- 원격 push, PR 생성, Issue 게시, 배포, 유료 API 사용은 하지 않는다. 여기서 PR은 코드 변경 병합 요청인 Pull Request다.
- 인간 이름·승인·평가 결과를 생성해서 정답 검토가 완료된 것처럼 만들지 않는다.

### 첫 실행에서 실제로 끝내야 할 것

`코드 감사 → 데이터 동결 → 사례/질의 초안 동결 → 기존 검색 실행 → 사람이 보기 쉬운 검토 패키지 → 상태/관찰 보고`

사람 검토 전에도 단순히 “검토자가 필요함”이라고 멈추지 말고, 그 직전까지 자동으로 가능한 작업을 완료한다. 단, 해시·데이터 계약·자원 조건이 깨진 경우는 해당 게이트에서 멈춘다.

## 1. 확인한 현재 코드와 반드시 보존할 계약

[확인] 아래는 기준 커밋의 실제 파일을 읽어 확인한 내용이다. CLI 실행 시 로컬 HEAD와 미커밋 변경을 다시 확인한다. 파일의 상세 출처는 끝의 R1~R7에 있다.

| 기존 파일 | 확인 내용 | 실험에서의 의미 |
|---|---|---|
| `backend/app/github.py` | `GitHubClient.fetch`가 전체 상태(`state=all`)를 최신 생성순으로 가져오며 응답의 `pull_request` 항목을 제거한다. 다음 페이지는 GitHub가 제공한 링크를 따른다. | 페이지 한도에는 PR 응답도 포함된다. 반환된 Issue 수와 요청 항목 수를 혼동하지 않는다. |
| `backend/app/config.py` | 기본 `max_pages=20`, `model_name=intfloat/multilingual-e5-small`, `device=cpu`, 조각 길이 448, 중첩 64다. | 현재 설정을 보존한다. 로컬에서 다른 설정을 쓰면 실제 값을 별도 기록한다. |
| `backend/app/domain.py` | `is_bug`는 Bug 유형 또는 설정 레이블 일치로 판단한다. `issue_text`는 제목+본문, `query_text`는 문제/오류/환경을 구분자와 합친다. | 입력 필드를 받는 것이 환경 호환성 검증을 뜻하지 않는다. |
| `backend/app/search.py` | `SearchEngine.index` 내부에서도 Bug 필터를 적용한다. BM25는 기술 토큰 분리 및 양의 IDF 수식을 사용한다. `fuse`는 두 순위의 상위 50개에 `1/(60+rank)`를 합한다. | 전체 Issue 평가를 하려면 평가용 문서 선택 경로가 필요하다. 문서의 레이블을 조작해서 통과시키지 않는다. |
| `backend/app/semantic.py` | query/passage 접두사, 정규화 벡터를 사용한다. 질의·문서 조각 사이 최대 코사인 유사도를 Issue 점수로 쓴다. | 부분적인 유사성만 높아도 순위가 올라갈 수 있다는 가설을 시험하되, 점수 계산을 먼저 바꾸지 않는다. |
| `backend/app/storage.py` | 스냅샷은 저장소별로 저장되며 기존 버전 해시에 Issue 내용과 Bug 레이블 설정이 사용된다. | 서비스 데이터와 평가용 두 검색 범위가 서로 덮어쓰지 않게 격리해야 한다. |
| `evaluation/evaluate.py` | 기존 평가는 단일 `query_number → target_number` 관계를 사용한다. 질의도 스냅샷에 있어야 하며, 영어 질의는 Issue 제목·본문에서 생성한다. 스냅샷 밖 정답이나 Bug 필터 제외 정답은 제외된다. | 독립적인 자연어 질의, 다중 관련 문서, 수집 누락 포함 평가를 위한 별도 경로가 필요하다. |

지시:
- 현재 알고리즘을 일반적인 “순정 BM25”라고 부르지 말고 `current_bm25` 또는 구현 설정을 함께 보고한다.
- Hybrid는 RRF(Reciprocal Rank Fusion, 순위 역수 결합)다. BM25 점수와 코사인 점수를 직접 더하는 방식으로 바꾸지 않는다.
- 기존 50쌍 관련 경고를 “50개면 통계적으로 충분함”으로 해석하지 않는다.
- `score`, `excerpt`, 본문 전체, 댓글, 요약을 구분한다. 현재 검색 평가의 입력 문서는 제목+본문이다.
- 코드·테스트를 읽지 않은 경로나 명령을 기존 기능으로 가정하지 않는다.

## 2. 표준 해법을 가져오는 이유와 이번 적용의 한계

[확인] 정보 검색 평가에서는 사용자 정보 요구에 맞는 질의와 문서별 관련성 판단을 구성하고, 여러 검색 방식의 상위 결과를 모아 사람이 판정하는 풀링을 사용한다. [S1]

[확인] `BEIR: A Heterogeneous Benchmark for Zero-shot Evaluation of Information Retrieval Models(2021/NeurIPS Datasets and Benchmarks)`는 BM25를 포함한 다양한 검색 방법을 비교한다. 신경망 검색의 우수성을 미리 가정하지 않을 근거이지, 이 저장소에서 어떤 방법이 이긴다는 근거는 아니다. [S2]

[확인] `Beyond Accuracy: Behavioral Testing of NLP Models with CheckList(2020/ACL)`는 평균 정확도 외에 행동별 검사를 제안한다. [S3]

[추정·미검증] 이번 적용은 다음 세 원리를 결합한다.

| 원리 | 적용 | 더 단순한 대안과 차이 | 전이 한계 |
|---|---|---|---|
| 정보 검색 평가 | 상황 질의, 다중 관련 문서, Hit@5·nDCG@5 | 정답 Issue 하나의 순위만 보는 평가보다 실제 서비스 목표에 가깝다. | 사람이 만든 관련성 판단은 불완전하며 실제 해결 성공을 보장하지 않는다. |
| 소프트웨어/NLP 행동 검사 | 표현 유지 변형, 무관 정보 추가, 중요한 조건 변경 | 평균 점수만으로 드러나지 않는 조건 구분 실패를 본다. | 변형이 실제로 의미를 보존/변경하는지 사람 검토가 필요하다. |
| 누락과 조건부 평가의 분리 | 같은 원본 스냅샷의 전체 Issue와 Bug 필터 범위를 비교 | 검색되지 않는 문서의 문제를 모델 문제로 오해하지 않는다. | 원본 스냅샷 자체가 부분 수집이며, 표본 선택이 전체 사용자 분포를 대표하지 않는다. |

새 검색 방법을 제안하는 실험이 아니다. 표준 비교 및 진단 절차를 현재 프로토타입에 적용한다.

## 3. 가설·경쟁 설명·결정 연결

아래 전체는 [추정·미검증] 실험 가설이다.

| 질문 | 지지되는 결과 | 반대/대안 결과 | 다음 결정 |
|---|---|---|---|
| H1. 상황 설명만으로 유용한 Issue를 찾는가? | 오류 문자열 없이도 직접 관련 문서가 Top-5에 있음 | 구체적 문자열이 있을 때만 검색됨 | 입력 보조 또는 사용 범위 재검토 |
| H2. 언어 차이를 줄이는가? | 같은 정보의 한국어/영어에서 관련 문서가 유지됨 | 영어에서도 실패하거나 한국어만 실패함 | 언어 문제와 문제 구분 실패를 분리 |
| H3. 조건 정보를 이용하는가? | 재현 조건 추가 후 직접 관련 결과가 늘고 명백한 조건 불일치가 줄어듦 | 환경 토큰만 비슷한 문서가 상승함 | 입력 조합·조각 결합·조건 비교 중 후속 후보 결정 |
| H4. Bug 필터가 도움이 되는가? | 덜 관련된 문서를 줄이면서 직접 관련 문서를 유지함 | 유용한 질문/미분류 Issue가 제외됨 | 필터를 기본 강제 규칙으로 유지할지 판단 |
| H5. 단순 기준선보다 추가 가치가 있는가? | 특정 질의군에서 임베딩/Hybrid가 도움이 됨 | BM25와 무차이 또는 역효과 | 복잡한 검색 고도화 대신 근거 정리에 집중할지 판단 |
| H6. 불충분한 근거를 과신하게 만드는가? | 참고 후보와 확정 근거를 구분해서 표시 가능 | 무정답 통제에서도 높은 점수가 나옴 | 점수를 확률로 해석하지 않고 근거 부족 처리 필요성 검토 |

어떤 결과도 판단을 바꾸지 못하는 추가 실험은 만들지 않는다. 실패 사례를 보고 원인이라고 단정하지 말고, 가능한 원인과 직접 확인된 원인을 분리한다.

## 4. 범위·예산·중단 조건

### 4.1 고정 대상

- `opencv/opencv`
- `huggingface/transformers`
- 저장소별 6개, 총 12개 **개발용 사례**.
- 사례마다 기본 입력 3종, 검색 방식 3종.
- 동일한 원본 스냅샷에서 검색 범위 2종을 비교한다.

[추정·미검증] 논리적 검색 수:

`12 사례 × 3 입력 × 3 방법 = 검색 범위 하나당 108회`

`108 × 2 검색 범위 = 핵심 비교 216회`

앞서 정한 108회는 한 검색 범위 기준이다. 이번에는 Bug 필터의 영향을 분리하기 위해 같은 질의를 두 범위에 적용한다. 사례를 24개로 늘린 것이 아니며, 216회가 216개의 독립 표본인 것도 아니다.

### 4.2 운영 상한

다음은 [추정] 비용 통제용 상한이다. 예상 성능/소요 시간에 대한 보장이 아니다.

| 항목 | 상한/원칙 | 이유 |
|---|---|---|
| 본 수집 | 저장소별 기존 방식 최대 20페이지×100항목 | 서비스가 현재 검색할 수 있는 범위부터 평가 |
| 전체 GitHub HTTP 호출 | 첫 작업 최대 100회, 재시도 포함 | 기본 목록 최대 40회+메타데이터·근거 조회 여유. 실제 제한이 더 엄격하면 그 제한을 우선 |
| 사례 | 12개, 후보 검토용 목록은 최대 48개 | 두 저장소×세 유형×두 사례를 우선 확보 |
| 모델 | 기존 다국어 모델 하나 | 모델 선택 실험으로 범위 확대 방지 |
| 모델 학습/유료 생성 API | 각각 0회 | 검색 품질 진단에 불필요 |
| 추론 | 기존 CPU 설정, 새 GPU 사용 승인 없음 | 비용 변화 없이 현재 서비스 경로 확인 |
| 인덱싱+추론 누적 실행 시간 | 첫 작업 90분에서 체크포인트 저장 후 중단 | 무제한 대형 인덱싱 방지. 실제 시간은 소규모 측정으로 추정 |
| 대규모 순위/가중치 튜닝 | 0회 | 개발 표본에 맞춘 성능 포장 방지 |

지시:
- 먼저 20개 문서로 조각 수·추론 시간·메모리를 측정하고 전체 추정치를 보고한다. 긴 문서를 임의로 잘라 예산에 맞추지 않는다.
- 예산을 넘을 것으로 보이면 현재 자료·진행 상태를 보존하고 `BLOCKED_RESOURCE_BUDGET`로 보고한다. 수집 범위 확대는 별도 변경안이다.
- API 제한 시 헤더/오류를 기록하고 캐시를 보존한다. 토큰 교체·계정 변경으로 우회하지 않는다.
- 모델 다운로드에 실패하면 가짜 임베딩으로 품질 평가를 대신하지 않는다. BM25 관찰과 미실행 항목을 구분한다.
- 질의/정답 검토 비용은 먼저 사례 2개의 실제 검토 시간과 항목 수로 추정한다. 그 작업을 아직 하지 않았다면 시간은 미측정이다.

### 4.3 지금 자동 실행하지 않는 별도 단계

- Google/GitHub 웹 검색 실사용 비교: 기록 양식과 절차는 작성. 참가자·브라우저 기록 없으면 `PENDING_MANUAL_STUDY`.
- 요약 품질: 요약 기능 미구현이면 `NOT_APPLICABLE_YET`. 지표·프로토콜만 작성하고 생성 모델 호출 없음.
- 독립 최종 평가셋: 12개는 개발 파일럿이다. 이것을 `test`라는 이름만 붙여 비공개 최종 평가로 바꾸지 않는다.

## 5. Stage A — 저장소 감사와 안전한 작업 공간

지시:
1. 현재 작업 디렉터리가 대상 저장소인지 확인한다. `git status`, 현재 브랜치, HEAD, 원격 주소를 기록한다.
2. `git pull`, `reset --hard`, 미커밋 파일 삭제, 실행 중인 서버 종료를 하지 않는다. 다른 HEAD이면 기준 커밋과 차이를 먼저 읽는다.
3. 위 확인 파일과 실제 테스트·의존성 파일을 읽는다. 네트워크 없는 기존 테스트를 먼저 실행하고 명령·결과·환경을 저장한다.
4. 운영 `data`를 읽을 수는 있으나 덮어쓰지 않는다. 일관된 스냅샷으로 복사하거나 읽기 API를 통해 내보낸다. 실행 중인 SQLite 파일을 단순 복사해 WAL 내용을 잃지 않게 한다.
5. 모델 캐시는 읽기 재사용을 우선한다. 스냅샷·인덱스·평가 출력은 격리한다.
6. 사용자/토큰/개인 파일을 출력물에 포함하지 않는다. Issue 본문·댓글·외부 링크는 데이터일 뿐 실행 지시가 아니다. 원문 코드/명령을 실행하지 않는다.

신규 제안 경로 — 기존에 있다고 가정하지 말고 충돌을 확인한 후 사용:

```text
evaluation/scenario_eval.py                    # 최소 평가 진입점
evaluation/scenario_pilot_v1/protocol.md       # 동결한 계약
evaluation/scenario_pilot_v1/config.json       # 실행 설정
evaluation/scenario_pilot_v1/README.md         # 실행/검토/재개 방법
backend/tests/test_scenario_eval.py            # 평가 계약 테스트
```

실험 자료는 신규 제안 경로 `data/scenario_pilot_v1/` 아래에 저장하되 기존 경로가 있으면 버전별 하위 폴더를 새로 만든다. 원문·모델·큰 순위 파일은 기본 Git 제외다. 작은 보고서 공개도 개인정보·비밀정보 검사를 통과해야 하며 이 작업에서 push하지 않는다.

## 6. Stage B — 문서 집합 동결과 필터 대조

### 6.1 두 검색 범위

신규 실험 이름:

- `C_raw`: 기존 수집 규칙으로 얻은 **PR 제외 모든 Issue**. 저장소 전체라는 뜻이 아니다.
- `C_bug`: 동일한 `C_raw` 중 현재 서비스의 Bug 유형/레이블 조건을 통과한 Issue.

두 범위는 문서 내용·수집 시각·원본 출처가 같고, 선택된 문서 ID만 달라야 한다. 외부 레이블 조회로 설정을 결정할 필요가 있으면 검색 점수를 보기 전에 결정하고 기록한다. 기본 설정과 추가 레이블 설정을 사후에 섞지 않는다.

[확인] GitHub Issues API 응답에는 PR이 포함될 수 있고 `pull_request` 키로 구분한다. [S4]

지시:
- 새 수집 또는 기존 캐시 재사용 중 하나를 원본 스냅샷별로 고정한다. 오래된 캐시와 새 데이터를 같은 스냅샷처럼 섞지 않는다.
- 수집 시작/완료 시각, 각 페이지의 식별 정보, 응답 항목 수, Issue 수, Bug 수, 최신/최초 생성 시각, `partial`을 기록한다.
- 저장소명+Issue 번호로 문서 ID를 만든다. 저장소가 다르면 같은 번호여도 다른 문서다.
- 제목/본문이 빈 항목, 외부 첨부 없이는 이해할 수 없는 항목, 삭제·이동 항목을 집계한다. 모든 항목을 자동으로 버리지 말고 사례 적합성/검색 범위를 구분한다.
- `C_bug`에 문서가 0개면 정상적인 데이터 관찰이다. 전체 Issue로 몰래 fallback하지 않는다. 서비스의 실제 오류/안내와 평가의 빈 결과를 함께 기록한다.

### 6.2 사례 선택과 수집 편향을 구분

[추정·미검증] 핵심 12개는 우선 `C_raw`에서 순위 결과를 보지 않고 선정한다. 이는 **수집된 문서 내에서 상황 설명 검색과 필터 영향을 보는 조건부 파일럿**이다.

중요한 한계:
- 이 방식은 정답 문서가 `C_raw`에 존재하기 쉬운 표본 선택이다.
- 따라서 여기서 얻은 결과를 전체 GitHub 또는 실제 사용자 문제의 수집 충족률로 일반화하지 않는다.
- 수집 누락은 아래의 외부 역사 사례 점검과 별도로 보고한다.

### 6.3 이미 본 역사 사례는 별도 수집 범위 점검으로 사용

[확인] 아래 두 Issue의 본문을 2026-10-01에 읽었다. 증상이 실제로 보고됐다는 근거이며 현재 버전의 버그/해결 여부가 검증됐다는 뜻은 아니다. [I1, I2]

- `opencv/opencv#17687`: Windows에서 특정 웹캠을 `CAP_MSMF`/`CAP_ANY`로 여는 시간이 오래 걸리고 `CAP_DSHOW`는 다르게 동작했다는 보고.
- `huggingface/transformers#24694`: GPT-Neo 생성 입력에 왼쪽 패딩을 넣었을 때 출력이 반복적·부자연스러워졌다는 보고.

지시:
- `cohort=historical_probe`, `previously_exposed=true`로 분리한다.
- 두 문서가 `C_raw`/`C_bug`에 있는지 확인한다. 없으면 누락을 그대로 보고한다.
- 근거 확인을 위해 개별 Issue를 읽을 수는 있지만 **이 두 정답만 서비스 인덱스에 추가하지 않는다**.
- 이 두 사례의 성공/실패를 핵심 12개 평균에 넣지 않는다.
- 별도 전체 Issue가 필요한 상황은 변경안으로 남긴다. 정답만 주입한 작은 집합을 ‘대형 저장소 검색 성능’으로 보고하지 않는다.

## 7. Stage C — 12개 사례와 질의 작성

### 7.1 사례 구성

[추정·미검증] 저장소별 아래 세 유형을 두 개씩 선택한다.

| 유형 | 조건 | 사례 수 |
|---|---|---:|
| `error_literal` | 실제 오류 문구가 있고 검색 단서로 사용할 수 있음 | 2×2 저장소 = 4 |
| `symptom_without_error` | 복사할 핵심 예외 메시지 없이 오동작·느려짐·잘못된 출력 등으로 설명됨 | 4 |
| `condition_sensitive` | 같은 큰 증상이라도 발생 작업·설정·입력 방식·환경 등 중요 조건을 구분해야 함 | 4 |

유형이 겹치면 `condition_sensitive`를 우선하고, 나머지를 실제 오류 문구 존재 여부로 나눈다. 타입 선정 이유를 남긴다. 동일 원인·동일 스레드·명시된 중복 체인의 사례는 독립 사례로 중복 계산하지 않는다.

후보 목록을 순위 실행 전에 만든다. 메타데이터·원문을 보고 적합성을 검토하고, 고정 시드 `20261001`을 사용한 후보 순서에서 선택한다. 후보 제외 이유를 기록한다. 12개를 채우기 위해 버그·출처·관찰을 지어내지 않는다. 부족하면 실제 수와 빠진 유형을 보고하고 자동 범위 확대는 하지 않는다.

### 7.2 질의의 정보 계약

각 사례에 다음 세 가지를 만든다.

- `A_ko_symptom`: 한국어 문제 상황. 증상과 발생 작업은 포함하지만 구체적 오류 문자열·추가 환경 정보는 최소화한다. 사용자에게 자연스럽게 알려진 함수/모델명은 무조건 제거하지 않는다.
- `B_ko_context`: A의 정보 + **신고 당시 알 수 있었던** 오류·버전·환경·재현 조건.
- `C_en_context`: B와 같은 정보를 영어로 표현. C에만 원인 함수명·해결 버전·추가 설명을 넣지 않는다.

비교 의미:
- A↔B: 정보 추가의 효과. 언어가 같다.
- B↔C: 표현 언어의 차이. 정보량은 같다.
- A↔C: 언어와 정보가 함께 달라지므로 순수 언어 효과로 해석하지 않는다.

오류 문구형 4개에는 `D_error_only`를 보조 입력으로 추가할 수 있다. 기본 216회와 분리한다. 오류가 없는 사례에는 이 입력을 생성하지 않는다.

### 7.3 질의 출처와 누출 방지

지시:
- 가능하면 실제 사용자가 작성한 질의를 사용한다. 없으면 `query_origin=reconstructed_from_issue`로 명시한다.
- 신고자의 증상·예상 동작·실제 동작·알려진 환경만으로 질의를 재구성한다. 원인 결론, 해결 댓글, 정답 Issue 번호/URL/제목을 복사하지 않는다.
- 원문에 “이 설정에서는 되고 저 설정에서는 안 됨”이라는 당시 관찰이 있었다면 질의에 쓸 수 있다. 나중 댓글에서 제시된 해결 조치를 당시 관찰로 바꾸지 않는다.
- 정답 번호, 관련 문서 목록, 관련성 레이블은 질의 encoder에 절대 전달하지 않는다.
- 질의 작성 모델/담당자가 이미 전체 원문을 봤다면 `author_exposure`에 기록한다. 실제 블라인드 작성이라고 주장하지 않는다.
- 순위를 보고 질의를 수정하지 않는다. 모호함·번역 오류 때문에 수정했다면 사유와 새 해시를 남기고 영향받는 검색/관련성 판단을 다시 만든다.
- 실제로 읽지 않은 외부 링크의 내용을 포함하지 않는다. 버전별 원문이 복원되지 않으면 ‘최초 신고 원문 재현’이 아니라 ‘현재 본문에서 발췌한 관찰 기반 질의’라고 쓴다.

### 7.4 자기 문서 검색과 중복 검색을 혼동하지 말 것

- 이번 핵심 파일럿에서 기존 Issue를 바탕으로 재구성한 새로운 질의는 그 원본 Issue를 후보에 둘 수 있다. 이것은 **기존 사례 검색/재구성 질의 회수**다.
- 그 결과를 독립 실사용 질의 성능이나 새로운 중복 Issue 탐지 성능이라고 부르지 않는다.
- 기존 duplicate pair 평가처럼 Issue 전체를 query로 쓰는 작업은 질의 Issue 자체를 제외해야 한다. 이번 경로와 섞지 않는다.
- 원본 문서를 제외한 후에도 유용한 별도 문서가 있는지 보는 검사는, 사람이 다른 관련 문서를 확인한 경우에만 별도 확장으로 둔다. 임의 제외 후 무조건 실패라고 계산하지 않는다.

### 7.5 검토 대상 예시 — 이미 본 역사 사례, 핵심 12개와 별도

다음은 [추정·미검증] 재구성 질의이며 사람 승인/정답 판정 완료 자료가 아니다.

```text
역사 점검: opencv/opencv#17687

A: Windows에서 OpenCV로 USB 웹캠을 열면 처음 화면이 나올 때까지
   몇 분씩 걸려. 카메라를 여는 단계가 너무 오래 걸려.

B: Windows에서 OpenCV 4.3으로 USB 웹캠을 사용하고 있어.
   CAP_MSMF나 CAP_ANY로 열면 오래 걸리지만 CAP_DSHOW는 빨리 열려.

C: On Windows with OpenCV 4.3, opening my USB webcam takes several minutes
   with CAP_MSMF or CAP_ANY, while CAP_DSHOW opens it quickly.
```

```text
역사 점검: huggingface/transformers#24694

A: GPT-Neo로 문장을 생성하는데 입력 길이를 맞추려고 왼쪽에 패딩을
   넣었더니 같은 단어를 반복하면서 이상한 문장을 만들어.

B: Transformers 4.28.1에서 GPT-Neo를 사용하고 있어.
   패딩 없는 입력에서는 문장이 자연스러운데, pad_token을 eos_token으로
```

C는 검색용 동등 정보 질의이지 원문 인용문이 아니다. 요약 과정에서 원문의 중요한 조건을 잃었는지 별도 검토한다.

## 8. Stage D — 신규 평가 데이터 계약과 사람 검토

아래 경로·키·상태는 **신규 제안**이다. 기존 API/DB 컬럼이라고 가정하지 않는다. 같은 목적의 기존 구조가 있다면 재사용하되 대응표를 남긴다.

### 8.1 최소 데이터 파일

```text
manifest.json              # 코드·환경·모델·스냅샷·설정의 식별 정보
cases.jsonl                # 원래 문제 사례와 근거, 선택 이유, 노출 상태

review_items.jsonl         # 사람이 검토할 질의-문서 쌍, 기본 grade=null
human_reviews.csv          # 실제 사람이 제출/수정한 판단 원본
qrels.jsonl                # 검증·조정 완료된 관련성 판단
coverage.csv               # 수집·필터·인덱스·상위 결과로 이어지는 경로

status.json                # 완료·대기·차단 상태와 재개 명령
```

검토 도구를 새 웹서비스로 만들지 않는다. 정적 HTML+CSV로 충분하면 그것을 사용한다. HTML에 원문을 표시할 때 스크립트/외부 자원 실행을 막고 텍스트로 안전하게 표시한다.

### 8.2 사례/질의의 최소 필드

지시:
- 사례: `case_id`, `family_id`, `repository`, `stratum`, `cohort`, `query_origin`, `source_urls`, `source_doc_ids`, `observation_evidence`, `author_exposure`, `selection_reason`.
- 질의: `query_id`, `case_id`, `variant`, `language`, `problem`, `error`, `environment`, `query_text`, `query_sha256`, `query_review_status`, `query_review_evidence`.
- 실제 검색 입력은 세 필드를 기존 `query_text`와 같은 규칙으로 조합한다. 저장된 `query_text`와 실제 encoder 입력이 일치하는지 검증한다.
- A의 질의가 요구하는 정보와 B의 질의가 요구하는 정보는 다를 수 있다. 관련성 정답도 질의별로 관리한다.
- B와 C의 관련성 판단은 사람이 정보 동등성을 확인한 경우에만 같은 정보 요구로 공유할 수 있다. 영어라는 이유만으로 기존 Issue 제목·본문으로 대체하지 않는다.

질의 검토에서는 ‘증상 충실성’, ‘숨겨진 해결 정보 유입’, ‘A→B 정보 추가 내용’, ‘B↔C 정보 동등성’, ‘중요 조건 누락’을 확인한다.

### 8.3 검색 기록 필드

최소 기록:

`run_id, query_id, query_sha256, repository, corpus_scope, corpus_hash, selected_doc_ids_hash, method, model_revision, code_revision, config_hash, status, error_code, elapsed_ms, returned_count, ranked_results`

각 결과에는 `rank, doc_id, score, score_type`을 남긴다. 동일 입력에서 방법별 점수 크기를 직접 비교하거나 확률로 표시하지 않는다.

- Top-5: 사람이 검토할 주 결과.
- Top-20: 후보 검색 단계 진단용으로 저장.
- 전체 순위가 이미 계산된다면 전체를 저장해도 되지만, 보지 않은 문서까지 관련성이 검증된 것으로 간주하지 않는다.
- 오류가 나면 `results=[]`만 남겨 정상적인 무검색 결과처럼 숨기지 않는다. `execution_error`, `empty_corpus`, `no_lexical_match`, 정상 반환을 구분한다.

### 8.4 관련성 판정 기준

[추정·미검증] 다음 판정표를 질의·문서 검토 전에 동결한다. 파일럿에서 정의 자체를 수정해야 하면 버전을 바꾸고 전체 관련 항목을 재검토한다.

| grade | 의미 | 판정 설명 |
|---|---|---|
| 2 | 직접 관련 | 입력한 증상·작업·중요 조건을 구체적으로 다뤄 다음 확인/비교에 유용함. 동일 원인 확정이나 해결 성공을 뜻하지 않음. |
| 1 | 주제 관련 | 같은 라이브러리·기능·포괄적 증상을 다루지만 입력 문제의 구분에 부족함. |
| 0 | 무관 | 다른 문제이거나 핵심 조건에 명백히 맞지 않음. |
| null | 미판정 | 아직 보지 않음, 자료 불충분, 의견 미조정. 0으로 자동 치환하지 않음. |

별도 필드:
- `condition_relation`: `supports | conflicts | unknown | not_applicable`.
- `evidence_scope`: `title_body | comment_only | unavailable`.
- `evidence_quote`: 판단을 지지하는 최소한의 원문 구간.
- `evidence_url`, `reason`, `reviewer_type`, `reviewer_id`, `reviewed_at`, `review_status`.

지시:
- 버전이 다르다는 사실만으로 무관이라고 처리하지 않는다. 해당 차이가 문제를 구분하는 근거인지 확인한다.
- 질의에 없는 조건을 마음대로 가정해서 후보를 감점하지 않는다.
- 문서가 같은 단어를 많이 사용한다는 이유만으로 grade=2를 주지 않는다.
- 댓글에서만 해결 정보가 보이면 `comment_only`로 기록한다. 이번의 제목+본문 검색 관련성과 ‘댓글까지 읽은 해결 유용성’을 섞지 않는다.
- 검색 관련성은 일차적으로 본문에서 확인한 증상·작업·조건으로 판단한다. 해결 정보의 출처/정확성 평가는 후속 별도 작업이다.
- 모순된 조건이 있어도 비교·원인 배제에 직접 유용한 문서라고 사람이 판단할 수 있다. 이때 그 근거를 적고 단순 문자열 불일치 규칙으로 덮어쓰지 않는다.

### 8.5 풀링과 블라인드 검토

[확인] 풀링은 여러 시스템이 반환한 후보를 합쳐 사람이 관련성을 판단하는 표준 접근이다. 완전한 관련 문서 목록을 보장하지 않는다. [S1]

지시:
1. 모든 핵심 방법·두 검색 범위의 **Top-5 합집합**과 별도로 알고 있는 근거 문서를 질의별 검토 대상으로 만든다.
2. B/C가 동등한지 아직 검토되지 않았다면 자동으로 같은 정답을 공유하지 않는다.
3. 검토 화면에서 검색 방법·순위·점수·정답 출처로 선택된 문서 여부를 가린다. 질의와 원문 문서, 출처 링크는 보여준다.
4. 순서는 고정 시드로 섞고 원래 출처/순위 대응은 별도 파일에 보관한다.
5. AI가 만든 grade 제안은 사람 검토 화면에 기본 노출하지 않는다. 필요하면 별도 `machine_judgments`로 격리한다.
6. 실제 사람 2명이 가능하면 독립 검토하고 불일치를 조정한다. 1명만 가능하면 `single_human_reviewer`라고 보고하고 모든 결과를 예비 결과로 제한한다. AI 2개를 사람 2명으로 세지 않는다.
7. 시스템이 처음 추천하지 않은 관련 문서가 발견되면 공통 qrels에 추가하고 모든 방법을 다시 계산한다. 특정 방법에만 정답을 추가하지 않는다.

검토량 상한의 의미:
- 핵심 결과는 `12×3×3×2×5=1,080`개의 반환 슬롯이다.
- 중복 문서 제거와 B/C 동등성 공유로 실제 검토 쌍은 줄 수 있지만, 줄어드는 양은 아직 모른다.
- 질의별 별도 근거 문서도 추가된다. 사람 검토가 “몇 분이면 된다”고 가정하지 않는다.
- 부담이 크면 2개 사례로 검토 시간을 먼저 측정하고, 완료한 사례 수를 드러낸 부분 보고서를 만든다. 고득점 사례만 골라 검토하지 않는다.

### 8.6 인간 검토 없이 가능한 것과 불가능한 것

가능:
- 실제 API 반환 여부, 문서 포함 여부, 원문 존재 여부 확인.
- 실제 검색 순위·응답 시간 출력.
- **참고 원본 문서의 회수 순위**를 별도 진단 값으로 기록.
- 질의/관련성 초안과 사람이 검토할 근거 정리.

불가능:
- CLI 스스로 `reviewer_type=human`이나 사람 승인 증거를 채움.
- 임베딩 유사도를 정답 관련성으로 재사용.
- 제목에 같은 단어가 있다는 이유로 gold 정답 확정.
- 정답 검토 없이 ‘상황 설명 검색 정확도’를 확정.

검토 자료를 사용자에게 받은 날짜·파일 해시·실제 입력 이력을 남긴다. 자동 검증은 형식과 provenance를 검사하는 것이지 인간 검토의 진실성을 스스로 증명하는 기능이 아니다.

## 9. Stage E — 기존 검색기를 보존하는 실험 구현

### 9.1 최소 변경 원칙

지시:
- 신규 `evaluation/scenario_eval.py`를 중심으로 구성하고 기존 기능을 재사용한다.
- 새로운 데이터베이스 서버·벡터 DB·프런트엔드 프레임워크를 추가하지 않는다.
- `C_raw`는 현재 `SearchEngine.index`의 Bug 필터 때문에 그대로는 평가할 수 없다.
- 해결은 **문서 집합 선택과 순위 계산을 분리하는 최소 공통 함수/평가 어댑터**다. 기본 서비스 호출은 기존 Bug 동작을 유지한다.
- 모든 문서에 가짜 bug 레이블을 붙이거나 `is_bug`를 전역 monkey patch하지 않는다.
- 기존 BM25 토큰화·IDF, 임베딩, 조각 결합, RRF 공식을 그대로 재사용한다.
- 공통화가 필요하면 기존 경로와 신규 어댑터가 같은 Bug 문서 집합에서 동일 순위/점수를 내는지 테스트한다. 구현 차이가 있으면 비교 실행 전 멈춘다.
- 실험을 위해 변경한 코드와 원본 서비스 기준 커밋을 모두 기록한다. 미커밋 변경이 있다면 diff 해시도 기록한다.

### 9.2 모델과 캐시

[확인] 현재 구현은 모델 revision과 텍스트 해시를 임베딩 캐시에 반영하고, 검색 시 revision 일치를 확인한다. [R4]

지시:
- 기존 모델 revision이 확보되어 있으면 사용한다. 없으면 다운로드 전에 사용할 revision을 한 번 결정하고 이후 고정한다.
- 벡터를 재사용할 때 모델명·revision·토큰화/조각 설정·텍스트 해시를 확인한다.
- `C_raw`와 `C_bug`는 같은 문서 벡터를 재사용할 수 있지만, candidate ID와 문서집합 해시 및 검색 통계는 분리한다.
- BM25의 문서 빈도/길이 통계는 각 corpus에서 다시 계산한다. 원본 corpus에서 점수만 매긴 뒤 Bug 아닌 결과를 사후 삭제하는 것은 `C_bug`와 동일하지 않다.
- corpus 선택 ID·scope를 캐시 식별에 포함한다. 현재 스토어 스키마만으로 격리가 불충분하면 평가용 메모리 스냅샷/별도 디렉터리를 사용한다.
- 기존 semantic corpus 캐시가 다른 scope를 섞지 않는지 테스트한다.
- E5 접두사 사용은 현재 코드를 따른다. 새 모델이나 다른 prefix를 실험하는 작업이 아니다.

### 9.3 실행 순서

1. 코드/환경 감사.
2. 원본 스냅샷 동결, corpus 두 종류의 ID/해시 생성.
3. 사례·A/B/C 초안 생성 및 해시 동결. 검토 상태를 정직하게 표시.
4. 스모크 테스트 2개 사례: 명령·데이터 흐름·캐시·ID 격리만 확인.
5. 문제 없으면 12개×3입력×3방법×2범위 실행.
6. Top-5 풀링, 정적 검토 화면·CSV 생성.
7. 정답 검토 자료가 없으면 관찰만 보고하고 `AWAITING_HUMAN_REVIEW`.
8. 검토 자료를 받으면 해시/질의 동등성/관련성 근거 검증.
9. 질의가 바뀌었다면 관련 run과 풀링을 다시 생성. 문서 판단만 바뀌면 고정 run에서 다시 채점.
10. 검토 완료 범위에 대해 지표·오류 분석·결정 보고.

초안 실행은 허용되지만, 사람이 검토한 지표와 별개의 상태다. 사람 검토를 기다리는 동안 모델을 바꿔 성능을 최적화하지 않는다.

## 10. 평가 지표와 분모 계약

[확인] 검색의 Recall은 전체 관련 문서 중 반환한 비율이며, 관련 문서가 하나인 경우에만 그 문서의 Top-K 포함 여부와 같아진다. nDCG는 관련성 정도와 순위를 함께 평가한다. [S5, S6]

아래는 [추정·미검증] 이번 파일럿의 평가 계약이다.

### 10.1 주지표 — Hit@5

질의 q의 Top-5 중 사람이 grade=2로 판단한 문서가 하나 이상이면 1, 그렇지 않으면 0이다.

```text
h(q, method, scope) = 1[Top-5 안에 grade=2 문서가 존재]
Hit@5 = sum(h) / 평가 가능한 질의 수
```

- 상위 5개를 모두 미판정 상태로 두고 h=0으로 채우지 않는다.
- 결과가 5개 미만이어도 실제 반환 결과를 판단한다. 빈 정상 결과 또는 빈 corpus는 해당 과제 성공 h=0이며 별도 이유를 기록한다.
- 실행 오류는 순위 품질 지표에서 `null`이다. **전체 시도 성공률**에서는 실패로 남기고 `execution_error_count`를 함께 보여준다. 실패한 방법의 질의를 조용히 제거해 성능을 높이지 않는다.

필수 보고:
1. `Hit@5_all_reviewed_tasks`: 동결된 12개 핵심 사례의 검토된 질의 전체. Bug 필터 때문에 근거가 빠진 질의도 유지한다.
2. `Hit@5_known_available`: 해당 scope의 검토된 문서 중 grade=2가 존재한다고 확인된 질의만의 조건부 값.
3. `availability_known_positive / total`: 조건부 값의 분모와 제외 이유.
4. 방법 비교 시 공통 질의 집합의 결과, 실패/미검토를 포함한 전체 상태표.

핵심 사례는 수집된 문서에서 선정했으므로 `all_reviewed_tasks`를 실제 사용자 전체 성공률로 표현하지 않는다.

### 10.2 보조지표 — pooled nDCG@5

등급 g∈{0,1,2}, 이득 `2^g - 1`을 사용한다.

```text
DCG@5 = Σ(i=1..min(5,반환수)) (2^grade_i - 1) / log2(i+1)
nDCG@5 = DCG@5 / IDCG@5
```

- IDCG는 **그 질의에 대해 공통 풀링·근거 확인으로 판단한 문서**를 이상적으로 정렬해 계산한다.
- 비교하는 방법/검색 범위별로 유리한 정답 집합을 새로 만들지 않는다. 두 scope 비교의 공통 기준 문서집합은 동결 `C_raw`다.
- 따라서 Bug 필터로 유용한 문서가 빠지는 영향도 이 공통 기준 nDCG에 반영된다. 이것은 필터+검색 전체의 품질이지 순수 순위 알고리즘 효과만은 아니다.
- 순위 효과만 보려면 두 scope 모두에서 직접 관련 문서가 확인된 동일 질의의 조건부 비교를 별도 표시한다.
- IDCG=0이면 `null`, 사유 `no_positive_gain_in_judged_reference`로 표시하고 별도 집계한다. 1로 채우지 않는다.
- 미판정 Top-5 문서가 있으면 해당 nDCG는 확정하지 않는다. 다른 방법까지 비교할 때 같은 qrels 버전을 사용한다.
- ‘pooled’를 지표명과 보고서에 붙인다. 전체 corpus의 모든 관련 문서가 확인됐다는 의미가 아니다.
- grade=1만 있는 문서들로 nDCG가 높아질 수 있으므로, 직접 관련성을 보는 Hit@5와 함께 읽는다.

### 10.3 순위 진단값

- `reference_doc_rank`: 질의 작성에 참고한 문서의 실제 순위. 관련성 품질과 구분하는 진단값.
- `first_direct_rank_within20`: 검토한 Top-20 안의 첫 직접 관련 문서 순위. Top-20 전체를 검토하지 않았으면 미확정.
- `candidate_direct_found_at20`: Top-5 실패가 상위 후보 안에는 있는지 보는 값. 추가 검토가 없다면 `unknown`.
- 상위 50개씩의 결합 후보에 없는 문서에 대한 Hybrid rank를 전체 corpus 순위인 것처럼 만들어내지 않는다.

### 10.4 집계와 불확실성

지시:
- A/B/C별, 저장소별, 유형별 원수치 n/N과 결과를 먼저 제시한다.
- 같은 사례의 번역·변형·반복 실행은 독립 표본이 아니다.
- 한 요약값이 필요하면 사례 안 평균 → 12개 사례 평균 순으로 계산하고 정의를 적는다. A/B/C별 표를 생략하지 않는다.
- 동일 사례 기준 Hybrid-BM25, Semantic-BM25의 승/동률/패 사례와 실제 차이를 제시한다.
- 비율 차이는 퍼센트포인트로 표시한다. 작은 분모에서 상대 개선율이나 ‘N배’를 강조하지 않는다.
- 이 파일럿에서는 p-value나 유의성 합격선, 80% 같은 임의 성공선을 만들지 않는다.
- 단지 12개에서 차이가 없다는 이유로 ‘효과가 없음’을 확정하지 않고, 관찰 범위와 부족한 근거를 보고한다.
- 최종 평가를 확장할 때는 원인/사례 가족 단위의 분리와 표본 설계가 먼저다. 이미 본 12개를 무작위 70/30으로 나눠 새 테스트로 만들지 않는다.

## 11. 추가 진단 실험 — 필요 조건이 충족될 때만

아래는 [추정·미검증] 사전 정의된 진단이다. 사례 수를 채우기 위해 부적절한 변형·음성 문서를 만들지 않는다. 미충족이면 `NOT_APPLICABLE`과 이유를 적는다.

### E0. 수집·필터·인덱스 경로 점검

각 질의의 알려진 관련 문서를 다음 상태로 분리한다.

```text
SOURCE_UNAVAILABLE
OUTSIDE_RAW_SNAPSHOT
REMOVED_BY_BUG_FILTER
IN_SCOPE_BUT_INDEX_MISSING
IN_INDEX_BELOW_TOP5
IN_TOP5_BUT_NOT_DIRECTLY_RELEVANT
HIT_DIRECT
UNJUDGED
EXECUTION_ERROR
```

여러 원인이 동시에 있으면 복수 플래그를 남긴다. 하나의 알려진 문서가 빠졌어도 다른 유용한 문서를 찾았다면 그 질의 전체를 검색 실패라고 하지 않는다. `known reference 누락`과 `사용자 정보 요구 충족`을 구분한다.

### E1. 표현 유지·무관 정보 추가

대상은 결과를 보기 전에 선택한 4개 사례다: 저장소별 오류 없는 상황 사례 1개 + 조건 의존 사례 1개.

각 사례의 B에서 두 변형을 만든다.
- `paraphrase`: 정보는 같고 말하는 방식만 다름.
- `irrelevant_append`: 사용자 식별자가 없는 합성 경로 또는 예의 문구 등 문제에 무관하다고 검토된 내용을 소량 추가.

`4 사례×2 추가 질의×3 방법×2 범위 = 최대 48회`.

지시:
- 버전·에러 코드·단위·tensor shape 등 의미가 있는 값을 무관 정보로 바꾸지 않는다.
- 개인정보 노이즈 실험에는 실제 인물/개인 경로가 아니라 `sample_user` 같은 합성 값을 사용한다.
- 변형을 검색하기 전에 원본과 정보 동등성을 검토한다. 사람 검토 전 결과는 탐색 기록일 뿐이다.
- 완전히 같은 순위를 요구하지 않는다. 원래 있던 직접 관련 Hit의 소실/회복, 상위 결과의 직접 관련성 변화를 본다.
- 실제 노이즈 빈도나 실패 기여율을 추정하는 실험은 아니다. 스트레스 검사라고 보고한다.

### E2. 중요한 조건이 다른 대조 사례

저장소별 최대 1쌍, 총 최대 2쌍을 구성한다. 두 질의 각각에 대해 유용한 문서를 실제로 확인해야 한다.

예시 아이디어: ‘카메라를 여는 단계가 느림’ vs ‘카메라는 바로 열리지만 재생 화면이 지연됨’. 후자 근거를 아직 확인하지 않았으면 완성된 정답 쌍으로 쓰지 않는다.

`2 대조쌍×2 질의×3 방법×2 범위 = 최대 24회`.

판정:
- 두 질의에 동일한 관련 문서가 가능하면 순위가 꼭 뒤집혀야 한다고 가정하지 않는다.
- 특정 문서가 한 질의에는 직접 관련이고 다른 질의에는 핵심 조건이 맞지 않는다는 근거가 있을 때만 그 대조를 평가한다.
- 현상·조건 부합 정도와 근거를 기록한다. 이 결과로 모델의 ‘이해 능력 전반’을 주장하지 않는다.

### E3. 근거가 없는 작은 문서 집합

저장소별 검토 완료 사례 1개씩, 총 최대 2개를 사용한다.

1. 고정 시드·규칙으로 최대 20개 문서의 작은 집합 `C_small_plus`를 구성한다. 관련 문서와 검색에서 혼동되는 문서를 포함할 수 있으며 선택 규칙을 기록한다.
2. 그 질의에 대해 집합 전체를 사람이 검토한다.
3. grade=2 문서를 **전부** 제거하여 `C_small_minus`를 만든다. 남은 문서를 다시 검토한다.
4. 같은 질의에 세 검색 방식을 plus/minus 각각 적용한다.

`2 질의×2 작은 집합×3 방법 = 최대 12회`.

지시:
- 같은 단어가 없는 엉뚱한 문서만 모아 쉬운 음성 검사를 만들지 않는다.
- 남은 문서 중 하나라도 직접 관련성이 미판정이면 ‘무정답 확정’으로 채점하지 않는다.
- plus/minus는 문서 집합이 다른 통제 실험이다. 모델 원인이 밝혀졌다고 해석하지 않는다.
- 반환 수·점수·후보 문서·화면 안내를 기록한다. 결과를 반환했다는 사실만으로 오류라고 하지는 않는다.
- 점수와 화면 표현이 “해결 확정”으로 오인될 여지를 확인한다. 현재 후보 검색기에 없는 거절 기능을 만들어 넣고 테스트하지 않는다.
- 결과: `통제 문서집합에서 직접 관련 근거 없음`. ‘GitHub 전체에 같은 문제 없음’이 아니다.

### E4. 긴 문서/질의 조각의 영향

새 검색 방법을 추가하지 않고 현재 최대 조각 점수를 진단한다.

지시:
- 모든 핵심 결과에 질의·문서의 토큰 수/조각 수를 기록한다.
- 가능하면 Top-5 점수를 만든 질의 조각/문서 조각의 인덱스와 최소 인용 구간을 저장한다.
- 해당 구간이 증상인지 환경·체크리스트·상투문구인지 검토한다.
- 문서 길이가 길고 점수가 높다는 관찰만으로 길이가 원인이라고 단정하지 않는다.
- E1의 불변 정보 추가 전후 결과와 함께 원인 가설을 정리한다. 무조건 최대 점수를 평균 점수로 바꾸지 않는다.

### E5. 응답 시간과 실행 무결성

- 기본 216회에서 개별 응답 시간과 예외를 기록한다.
- 저장소×유형을 대표하는 사전 선택 6개 질의에 대해 `C_raw`에서 세 방법을 준비 상태로 각 3회 측정한다: 54회.
- 모델/프로세스 첫 로딩 시간은 저장소×방법별 최대 1회씩, 총 6회 별도 측정한다. 모델 다운로드 시간은 따로 기록한다.
- 타이밍 재실행은 새 독립 질의가 아니며 검색 품질 표본 수에 더하지 않는다.
- method 실행 순서를 고정 시드로 바꾸고 모델 캐시·프로세스 상태를 기록한다. CPU·메모리·라이브러리 버전을 표시한다.
- 표본이 작은 지연시간 결과를 운영 환경의 안정적인 P95 성능으로 홍보하지 않는다. 개별값·중앙값·범위를 우선 보여준다.

## 12. 외부 검색 비교와 요약 평가 — 이번에는 준비 범위

### 12.1 외부 검색의 추가 가치 비교

[확인] Google도 의미/개념 표현을 이용하는 검색 시스템을 설명한다. 따라서 내부 BM25 비교만으로 일반 웹 검색보다 낫다고 주장하지 않는다. [S7]

[추정·미검증] 준비할 기록 양식:

`participant_id, case_id, tool, order, exact_queries, started_at, finished_at, opened_urls, useful_evidence_found, condition_understood, evidence_url, unresolved_questions`

지시:
- 원문을 이미 알고 있는 CLI가 검색한 시간을 사람의 문제 해결 시간으로 기록하지 않는다.
- 같은 정보의 문제 설명·오류·환경을 양쪽에 제공한다.
- 일반 웹 검색이 GitHub 밖의 유용한 문서를 찾았다면 성공으로 인정한다.
- 키워드 재작성·영어 번역 등 실제 사용자가 할 수 있는 행동을 한쪽만 금지하지 않는다. 입력 변경과 도구 사용을 기록한다.
- 웹 검색에는 의도적으로 긴 원문만 넣고 우리 서비스에만 정리된 좋은 질의를 주지 않는다.
- 동일 참가자가 같은 문제의 답을 미리 배우지 않도록 사례/도구 순서를 교차 배정한다. 참가자가 없으면 진행하지 않는다.
- 최초에는 핵심 사례 중 사전 선택한 4개로 기록 절차가 가능한지만 점검하는 안을 제시한다. 표본 확장과 실제 사용성 결론은 후속 합의 대상이다.
- 검색만 비교하는 조건과 검색+요약 조건을 분리한다. 기존 검색에 기존 요약 도구를 함께 사용하는 대안도 후속 비교 후보로 남긴다.
- 브라우저 자동화나 검색 접근이 불가능하면 양식과 사용자 실행 방법을 남긴다. 결과/시간/순위를 추측하지 않는다.

### 12.2 요약 품질

[확인] `Evaluating Verifiability in Generative Search Engines(2023/Findings of EMNLP)`는 생성 내용의 출처 지원 여부와 인용의 정확성을 구분한다. [S8]

지시:
- 요약 기능이 없으므로 이번에 이를 구현하거나 유료 모델을 호출하지 않는다.
- 나중에 같은 문서+댓글을 제공한 상태에서 원문/핵심 문장 발췌/생성 요약을 비교한다는 프로토콜만 작성한다.
- 원인 확정 여부, 사용자 제안과 유지보수자 확인의 구분, 임시 우회법과 공식 수정의 구분, 버전·조건·미확인 사항·원문 위치를 평가 항목으로 둔다.
- 검색 실패와 요약 실패를 분리하기 위해 먼저 동일한 문서 입력을 사용하고, 그다음 실제 검색 결과를 사용한 전체 흐름을 평가한다.
- 이번 보고서에는 `해당 없음, 이유: 요약 기능 미구현으로 이번 실행 대상 아님`이라고 쓴다. 품질 점수를 빈칸 대신 0으로 만들지 않는다.

## 13. 필수 자동 테스트

지시: 기존 테스트를 유지하고, 신규 평가 계약에 필요한 최소 테스트를 추가한다. 아래 기능별 테스트를 여러 작은 테스트로 나눌 수 있지만, 테스트 개수 자체를 목표로 삼지 않는다.

1. 독립적인 영어/한국어 `query_text`가 실제 검색 입력으로 사용되고 영어가 원문 제목·본문으로 치환되지 않는다.
2. 신규 상황 질의가 원본 corpus의 Issue 번호를 반드시 가질 필요가 없다.
3. 서로 다른 저장소의 동일 Issue 번호를 다른 문서로 구분한다.
4. 같은 문서 집합일 때 기존 서비스 경로와 평가 경로의 BM25·RRF 결과가 동일하다. 의미 경로도 같은 벡터/설정에서 동일 순위를 낸다.
5. `C_raw`/`C_bug` 선택이 원본 레이블·본문을 바꾸지 않고, 검색 인덱스 및 캐시를 섞지 않는다.
6. PR 제외가 유지되고, Bug 문서 0개·빈 corpus·무일치·실행 오류가 다른 상태로 저장된다.
7. 질의/원문/모델 revision/설정/코드 해시 불일치가 있으면 결과를 재사용하지 않는다.
8. 여러 grade=2 문서를 인정한다. 참고 원본 하나가 안 나와도 다른 직접 관련 문서가 있으면 Hit=1이다.
9. 모든 Top-5가 grade=0/1이면 Hit=0이며, 미판정 값이 있으면 자동으로 0 처리하지 않는다.
10. grade=2 문서가 Bug 필터로 빠진 질의가 전체 과제 결과에서 사라지지 않는다.
11. 작은 손계산 fixture에서 nDCG의 이득/할인/정규화가 맞고, 이상 순위는 1이다. IDCG=0은 null이다.
12. 실제 사람이 제공하지 않은 reviewer 정보로 확정 지표를 생성하지 않는다. machine judgment는 사람 qrels와 분리한다.
13. 질의 변경 시 이전 검색 결과와 qrels의 연결이 무효화되며, 번역·변형·반복 실행이 독립 사례로 집계되지 않는다.
14. 무정답 작은 집합에 grade=2 또는 미판정 문서가 남아 있으면 무정답 인증에 실패한다.
15. 검토 화면에 원문 HTML/스크립트가 실행되지 않고, 토큰·로컬 비밀정보가 출력되지 않는다.

테스트용 가짜 임베딩은 계산 경로 검사에만 사용한다. 실제 검색 성능 결과에는 실제 고정 모델을 사용한다. ‘단위 테스트 통과’와 ‘사람이 유용한 문서를 찾았다고 확인함’을 다른 항목으로 보고한다.

## 14. 사람이 읽을 결과와 제안서에 쓸 결과

### 14.1 사례집이 숫자 표보다 먼저

12개 사례 전부에 아래 흐름을 제시한다. 성공 사례만 골라 보여주지 않는다.

```text
사례 ID / 저장소 / 유형 / 개발 표본이라는 상태
질의 A, B, C 원문
참고한 관찰 근거와 질의 작성 방식
검토된 직접 관련 문서 및 중요한 조건
C_raw 포함 여부 → C_bug 포함 여부 → 인덱스 포함 여부
방법별 Top-5: 실제 제목·번호·점수·관련성 판정·근거
찾은 것 / 놓친 것 / 아직 모르는 것
관찰된 실패 위치
경쟁 설명과 이를 구분할 최소 후속 확인
다음 결정
```

그림이 필요하면 실제 결과에서만 만든다. 가상의 개선 수치로 표/그래프를 채우지 않는다.

### 14.2 최종 보고서 순서

1. 어떤 사용자 문제를 평가했는가.
2. 코드·모델·데이터·질의·관련성 판단의 버전과 실제 검토 상태.
3. 완료/미완료 실험 수, 원본 사례 수, 반복 검색 수, 실제 자원 사용량.
4. 수집·필터·실행 실패 현황.
5. 같은 조건의 BM25/의미/Hybrid 결과와 사례별 승/동률/패.
6. 입력 정보·언어·표현·조건 변화 검사.
7. 과신/무정답 검사와 한계.
8. 원인으로 확인된 사실과 아직 가설인 설명.
9. 유지/조건부 유지/보류/기각할 작업과 판단을 바꿀 증거.
10. 제안서에 쓸 수 있는 문구와 아직 쓸 수 없는 주장.

### 14.3 결과별 결정 기준

[추정·미검증] 여기에는 임의 합격 점수를 두지 않는다. 다음 행동과 근거의 연결로 판단한다.

| 관찰 | 우선 결정 | 아직 단정하지 않을 것 |
|---|---|---|
| 근거가 원본 수집 범위 밖 | 수집 계약·범위를 먼저 검토 | 임베딩 실패, 전체 GitHub에 문서 없음 |
| C_raw에서는 직접 관련, C_bug에서 제외 | Bug 필터 강제 여부를 검토 | 무조건 전체 Issue가 더 좋음 |
| 영어 B동등 입력은 되지만 한국어가 어려움 | 번역 대안/다국어 검색 검토 | 상황 이해 능력 전체 부족 |
| B의 조건 추가가 도움이 됨 | 작은 입력 보조 우선 | 대화형 에이전트가 필수 |
| 최대 점수 구간이 환경/상투문구에 치우침 | 해당 사례의 조각 결합/입력 처리 대조 검토 | 로그 전체 파서 필요 |
| BM25와 Hybrid가 비슷하거나 Hybrid가 나쁨 | 단순 방법 유지 또는 적용 조건 제한 | 프로젝트 자체가 무의미함 |
| 기존 웹 검색과 차이가 없음 | 근거 확인/요약 통합 가치 별도 평가 | 검색 정확도 우위 |
| 사람 검토 없음/불충분 | 검토 패키지를 전달하고 결론 보류 | 자동 점수를 인간 검증 성능으로 표시 |

추가 모델·규칙을 실행하려면 먼저 어느 실패를 고치려는지와 최소 비교를 변경안으로 보고한다. 이 파일럿의 결과를 보고 기준/질의/분모를 소급해서 바꾸지 않는다.

### 14.4 제안서용 요약 초안

다음 문구는 ‘수행 방법/테스트 계획’에 쓸 수 있는 계획 문구다. 결과 완료 문구로 바꾸지 않는다.

> 실제 공개 Issue에 근거한 오류 문구형·상황 설명형·조건 의존형 질의를 구성하고, 같은 문서 집합에서 키워드·의미·결합 검색을 비교한다. 수집 누락과 Bug 필터 제외를 검색 순위 실패와 구분하며, 상위 결과의 직접 관련성과 입력 표현·조건 변화에 따른 동작을 평가한다. 개발 파일럿의 판단 결과에 따라 수집 범위, 입력 보조, 검색 방식의 개선 우선순위를 결정한다.

확인 결과가 없는 상태에서 쓰지 않을 문구:
- ‘오류 원인을 이해하고 자동 해결한다.’
- ‘Google보다 정확하다.’
- ‘한국어 설명으로 모든 GitHub 버그를 찾는다.’
- ‘12개 파일럿에서 높은 점수이므로 검증 완료.’

## 15. CLI 진입점과 재개 방법

아래는 **새로 구현할 CLI 계약 예시**다. 현재 저장소에서 이미 실행되는 명령이라고 가정하지 않는다. 구현 후 `--help`와 스모크 실행으로 실제 명령을 확인해 README와 최종 보고서에 적는다. 기존에 같은 기능의 명령이 있으면 중복 구현하지 말고 매핑한다.

```text
python -m evaluation.scenario_eval prepare --config evaluation/scenario_pilot_v1/config.json --run-dir data/scenario_pilot_v1/run_001
python -m evaluation.scenario_eval retrieve --run-dir data/scenario_pilot_v1/run_001
python -m evaluation.scenario_eval export-review --run-dir data/scenario_pilot_v1/run_001
python -m evaluation.scenario_eval score --run-dir data/scenario_pilot_v1/run_001 --reviews <실제_사람이_작성한_검토파일>
python -m evaluation.scenario_eval diagnose --run-dir data/scenario_pilot_v1/run_001
python -m evaluation.scenario_eval report --run-dir data/scenario_pilot_v1/run_001
```

- OS와 가상환경은 실제 환경을 확인한다. 위 `python`은 그 환경의 인터프리터다. Windows/Linux 전용 절대 경로를 미리 가정하지 않는다.
- `prepare`: 감사·수집·초안 생성·동결. 수집만 필요한 경우 단계 재개가 가능하게 한다.
- `retrieve`: 현재 고정 검색기 실행. 검토 전 실행은 상태를 draft로 유지.
- `export-review`: 순위/방법을 가린 검토 자료. 사용자가 어떤 칸을 채워야 하는지 설명.
- `score`: 사람 검토 provenance와 해시를 검증. 미검토를 자동 확정하지 않는다.
- `diagnose`: 검토된 변형/대조/무정답 자료만 사용. 충족되지 않은 실험은 이유와 함께 건너뜀.
- `report`: 미완료도 포함한 현재 상태 보고서. ‘계획한 작업’과 ‘실제 실행한 작업’을 구분.

상태 코드 제안:

```text
PREPARED_DRAFT
RANKINGS_READY_UNREVIEWED
AWAITING_HUMAN_REVIEW
PARTIALLY_REVIEWED
PILOT_EVALUATED
BLOCKED_SOURCE_OR_CONTRACT
BLOCKED_RESOURCE_BUDGET
PENDING_MANUAL_STUDY
NOT_APPLICABLE_YET
```

`PILOT_EVALUATED`는 개발 표본의 평가가 완료됐다는 상태일 뿐, 서비스 우수성/배포 승인 상태가 아니다.

최종 CLI 응답에는 반드시 다음을 포함한다.
- 실제 생성/변경한 파일 경로와 변경 이유.
- 코드 기준 커밋·로컬 변경 상태.
- 실제 수집 범위·사례 수·검색 실행 수.
- 실제 테스트 실행 명령과 결과.
- 사람 검토 여부와 아직 계산하지 않은 지표.
- 실제 관찰에서 가장 의사결정을 바꾸는 문제 3개 이내.
- 사용자에게 필요한 최소 작업과 정확한 재개 명령.
- remote push/배포를 하지 않았다는 작업 상태.
