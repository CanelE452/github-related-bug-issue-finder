- 작성일: 2026-10-01
- 대상 저장소: `CanelE452/github-related-bug-issue-finder`
- 작성 시 확인한 원격 HEAD: `7ec06cac66c84eaea70495b2bb17ce693f3b679b`
- 기준 실험: `scenario_pilot_v1 / run_001`
- 작업 유형: 승인된 후속 작업 실행 인계 — **Phase 0 → 2 → 3**
- 이 문서는 CLI가 수행할 지시문이다. 새 실험이나 수정·push가 이미 완료됐다는 뜻이 아니다.

## 0. 시작할 때 고정할 목적과 승인 범위

### GOAL

**기존 검색 결과를 보존하면서 관련성 평가를 완료할 수 있게 만들고, 확인된 실패만 한 요소씩 바꾸어 비교한다. 결과·근거·실행 이력·실제 그림을 GitHub에 게시해 사용자가 구현 타당성과 검색 품질을 다시 검토할 수 있게 한다.**

독자는 사용자·팀원·담당 교수다. 결과로 결정할 것은 다음과 같다.

1. 상황 설명으로 유용한 기존 Issue를 찾는가?
2. 실패는 수집 범위, Bug 필터, 한국어 기술 토큰, 순위 결합, 질의 정보 부족 중 어디에 있는가?
3. 검색 수정이 실제로 도움이 되는가, 아니면 기존 단순 검색과 근거 정리로 충분한가?

검색 방법을 옹호하거나 성공 사례를 늘리는 것이 목적이 아니다. 무차이·역효과·평가 불가능도 보고한다. 로그 파서·새 모델·요약 모델을 먼저 붙여 문제를 덮지 않는다.

### 이번에 실행해도 되는 것

사용자는 다음 범위의 구현·검사·실험과 **GitHub push**를 요청했다. 같은 범위에 대해 계획 승인을 다시 반복해서 받지 않는다.

- 기존 실험 파일 및 운영 데이터 보존, 출처·해시 감사.
- 새 채점/보고 버전에서 부분 검토 처리와 보고서 상태 갱신 보강.
- 사람이 실제로 작성한 검토 파일을 가져와 채점. 없으면 검토 패키지·재개 명령까지 준비.
- 기준선의 기계적 진단과, 사람 근거 게이트를 통과한 실패에 대한 제한된 단일 변경 비교.
- 앞서 미실행이던 표현/조건/무정답 검사 도구를 완성하고, 입력 검증 조건이 충족된 검사만 실행.
- 기존 검색과의 수동 사용 비교 자료 준비 및 실제 제출된 기록의 분석.
- 결과 MD·CSV/JSONL·PNG·검토 가능한 근거·테스트 로그를 게시.
- 범위에 속하는 변경만 분리해서 커밋하고 안전한 브랜치에 push한 뒤 원격에서 확인.

### 이번에는 하지 말 것

- 운영 서비스의 기본 검색 방식·필터·UI를 평가 결과 없이 교체하지 않는다.
- 새 모델 학습, 미세조정, Cross-Encoder, 요약 모델/유료 생성 API, 범용 로그 파서를 추가하지 않는다.
- 전체 GitHub 크롤링이나 무제한 페이지 증가를 하지 않는다.
- 구 결과, 구 manifest, 구 질의, 사람 판정 원본을 덮어쓰거나 해시만 새 것으로 고치지 않는다.
- 실제 사람이 검토하지 않았는데 `reviewer_type=human`·이름·검토 시간을 만들어 넣지 않는다.
- AI 여러 개의 합의를 사람 여러 명의 독립 판정으로 보고하지 않는다.
- 무관한 미커밋 변경을 섞거나 `git add .`, 강제 push, 브랜치 보호 우회, 무단 배포를 하지 않는다.

### 가장 중요한 진행 규칙

**사람 검토 파일이 없어도 작업 전체를 멈추지 않는다.** 보존·채점 버그 수정·테스트·기계적 감사·검토 화면·상태 그림·문서까지 완료하고 **검토 대기 상태로 먼저 push**한다.

다만 사람이 판단해야 하는 관련성·변형 동등성·조건 대조 근거를 CLI가 대신 확정하지 않는다. 필요한 파일을 사용자가 제공하면 같은 명령으로 이어서 실행되게 만든다. 판정이 완료된 일부 사례만으로도 부분 결과를 낼 수 있지만, 같은 비교의 분모는 같아야 한다.

## 2. Phase 0 — 작업을 목적에 연결하고 불필요한 확장을 막기

| 행동 | 왜 필요한가 | 더 단순한 대안 / 불필요해지는 조건 |
|---|---|---|
| 입력·순위 보존 및 재채점 | 검색 결과와 채점 수정의 효과를 분리 | 저장된 결과로 채점 가능하면 216회 재추론하지 않는다. |
| 실제 관련성 검토 | 원문을 다시 찾음과 유용한 문제 사례를 찾음을 구분 | 숫자만 계산하려고 참고 원문에 자동 2점을 주지 않는다. |
| 공통 검토 목록의 완료 확인 | 덜 검토된 방법/질의가 유리해지는 비교를 방지 | 완료한 일부 질의로 먼저 보고하되 동일 분모를 쓴다. |
| 한국어 기술 토큰 진단 | 의미 검색 차이에 기본 문자열 처리 오류가 섞였는지 확인 | 재현되지 않으면 새로운 형태소 분석기/규칙을 넣지 않는다. |
| RRF 기여분 분석 | 결합 전에 있던 유용한 결과가 어디서 밀렸는지 확인 | 기존 단일 검색이 충분하면 복잡한 결합을 채택할 이유가 없다. |
| Bug 필터 대조 | 문서 누락과 순위 실패 구분 | 이미 저장된 두 scope 결과를 재사용한다. |
| 조건/무정답/외부 검색 비교 | 평균 점수 밖의 적용 조건과 실사용 가치를 확인 | 검증된 입력·실제 사람이 없으면 양식/대기 상태만 공개한다. |
| 결과 그림과 공개 증거 | 다음 검토자가 결과를 계산·추적할 수 있게 함 | 모든 그림은 실제 CSV/JSON을 근거로 하며 빈 정확도 그래프를 꾸미지 않는다. |

예상 가능한 무차이/역효과까지 포함해 보고한다. 처리 오류의 수정, 제한된 개발 표본에서의 개선, 독립적인 일반화 성능은 서로 다른 주장이다.

## 3. Stage A — 안전한 시작과 기존 결과 동결

### A1. 작업 트리 확인

1. `git status --short`, 현재 브랜치, `git rev-parse HEAD`, 원격 주소를 확인한다. 토큰이 포함된 URL은 로그에서 마스킹한다.
2. `git fetch`로 원격 상태를 읽되 자동 pull/merge/reset을 하지 않는다. 원격이 위 기준에서 달라졌다면 관련 파일 diff를 읽고 후속 버전의 출발점을 기록한다.
3. 기존 파일을 실제로 읽는다:
   - `backend/app/search.py`, `semantic.py`, `domain.py`, `storage.py`, `config.py`
   - `evaluation/scenario_eval.py`, `evaluation/scenario_report.py`
   - `evaluation/scenario_pilot_v1/README.md`, `protocol.md`, `config.json`
   - `backend/tests/test_scenario_eval.py`와 해당 경로에 실제 존재하는 테스트
   - `docs/experiments/scenario_pilot_v1/run_001/`의 보고서·manifest·질의·순위·검토 파일.
4. 미커밋 변경은 보존한다. 필요한 경우 clean worktree로 이번 작업만 분리한다. 실행 중인 앱/데이터베이스를 종료하거나 초기화하지 않는다.

### A2. 원래 run 자료 확보

- README가 안내한 로컬 `data/scenario_pilot_v1/run_001/`의 존재를 확인한다. 경로가 다르면 사용자에게서 이미 제공된 실제 위치를 먼저 확인한다.
- 원본 스냅샷, `runs.jsonl`, `queries.jsonl`, `cases.jsonl`, `review_items.jsonl`, 검토 파일, manifest, 캐시를 **읽기 전용 부모 실험**으로 취급한다.

- 공개된 순위·질의·범위 목록으로 구조 감사와 제한된 결과 확인은 진행한다.

## 4. Stage B — 검색 실행 버전과 채점/보고 버전 분리

### B1. 부모 데이터는 수정하지 않고 새 provenance를 생성

새 manifest에는 최소 다음을 기록한다. **신규 제안 필드**다.

- `parent_run_id`, `parent_report_commit`, `parent_manifest_sha256`
- `parent_rankings_file` / `parent_rankings_sha256` / 표현이 public인지 local인지
- `queries_hash`, `cases_hash`, `corpus_hashes`, `selected_doc_ids_hashes`
- `parent_retrieval_code_hashes`, `parent_model_revision`
- `scorer_version`, `scorer_code_hashes`, `reporter_code_hashes`, `scoring_config_hash`
- `review_schema_version`, `review_round_id`, `pool_version`, `qrels_version`
- `query_review_file_hash`, `review_input_hashes`, `adjudication_hash`
- 실제 실행 환경, 시각, 명령, 출처 검사 수준과 미충족 사항.

새 reporter 때문에 구 `verify()`가 거부한다고 기존 manifest의 `code_hashes`를 업데이트하지 않는다. 새 reader는 부모 입력 파일의 무결성을 검사하고, **부모 검색 버전과 새 채점 버전이 다르다는 사실을 명시적으로 허용·기록**해야 한다. `--skip-verify` 같은 우회로를 만들지 않는다.

구 결과와 연결되는 키(질의·문서·scope·모델·순위 파일)가 변하면 새로운 검색 실행이다. 해시가 다르지만 같다고 주장하지 않는다.

### B2. 재실행을 최소화

- 기존 216회 순위와 검토 자료가 검증되면 다시 모델 추론할 필요 없이 재채점한다.
- 후속 검색 변경을 평가하려면 고정한 질의 2개 × 3방법 × 2scope의 최대 12회로 기준선 재현을 먼저 확인한다. 선택은 사례 순서/고정 시드로 결정하고 파일에 남긴다.
- 동일 데이터·설정에서 상위 순서와 점수가 재현되는지 확인한다. 점수의 수치 허용 오차가 필요하면 실행 전에 이유와 값을 고정하고 보고한다. 의미가 다른 순위 변화를 반올림으로 숨기지 않는다.
- 재현 불일치가 있으면 새 방법과 구 결과의 직접적인 개선 비교를 중단한다. 원인과 새 환경 재기준선 필요성을 보고한다. 저장된 구 결과의 독립 감사까지 폐기할 필요는 없다.
- 공개 파일이 Top-20만 담고 있다면 21~끝 순위를 추측해서 RRF를 계산하지 않는다. 필요한 전체 순위는 검증된 부모 데이터·고정 모델로 새로 계산하고 별도 provenance를 남긴다.

## 5. Stage C — 실제 사람 검토를 재개하기 쉽게 만들기

### C1. 데이터 재사용과 검토 구분

- 실제 제공된 사람 검토 파일이 있는지 먼저 찾고 열어 본다. `.completed.csv`라는 이름만으로 완료라고 인정하지 않는다.
- 핵심 질의 목록은 파일에서 계산한다. 현재 알려진 36개를 코드에 하드코딩하지 않는다. 역사 사례 2개는 별도 cohort로 둔다.
- 관련성 검토는 현재 알려진 429개 쌍을 초기 공통 풀로 가져오되 실제 개수·고유키를 검산한다.
- A(한국어 증상), B(한국어 조건 추가), C(B와 동등하도록 작성한 영어)의 정보 계약을 보존한다. B/C가 동등하다는 실제 승인 없이는 qrels를 공유하지 않는다.
- 원문 작성자가 원인 분석·해결책까지 읽었거나 검토자가 이미 순위를 봤다면 `exposure` 기록을 남긴다. 이를 블라인드 검사라고 부르지 않는다.

### C2. 순위가 가려진 검토 패키지

순위·방법·점수·‘참고 정답으로 고른 문서’ 표시는 숨긴다. 질의, 원문 제목/본문, 출처, 검토 ID는 보여 준다. 정렬 시드는 고정한다.

최소 기능:
- 사례별 탐색, 완료/대기 표시, 실제 판정 입력/내보내기 또는 명확한 CSV 연결.
- 질의 충실성 검토와 문서 관련성 검토를 별도 표시.
- 초반 2개 사례의 검토 시간을 실제로 기록할 수 있는 양식. 사람이 시작/완료하지 않았다면 시간은 null.
- 계정·인증·대시보드 서버까지 만들지 않는다.
- Issue 안의 HTML/스크립트/명령은 실행하지 않는다. 원문은 안전한 텍스트로 표시한다.

검토 2개 사례는 점수를 기준으로 고르지 않는다. 고정 순서에서 저장소별 하나를 선택하고 기준을 기록한다. 이미 알려진 실패 사례를 별도 진단으로 먼저 보는 것은 가능하지만, 그 소수 결과를 전체 품질 대표 표본처럼 보고하지 않는다.

### C3. 기존 판정 기준을 그대로 유지

| 값 | 의미 |
|---|---|
| 2 | 증상·작업·중요 조건을 직접 다뤄 다음 확인/비교에 유용함. 동일 원인 또는 해결 성공의 확정이 아님. |
| 1 | 주제·기능은 관련되지만 입력 문제를 구분하기에 부족함. |
| 0 | 무관 또는 핵심 조건에 명백히 맞지 않음. |
| null | 미판정·자료 불충분·검토자 불일치 미조정. |

기존 `condition_relation`, `evidence_scope`, `evidence_quote`, `evidence_url`, `reason`을 유지한다.

- 질의에 없는 조건을 추측해 감점하지 않는다. 단순 버전 차이만으로 무관이라고 단정하지 않는다.
- 비교·원인 배제에 직접 유용한 반대 조건 문서는 근거를 쓰면 직접 관련일 수 있다. 규칙으로 일괄 제거하지 않는다.
- 본문 관련성과 댓글에서만 찾은 해결 정보의 유용성을 섞지 않는다. `comment_only`나 `unavailable`은 제목+본문 판정 완료의 대체가 아니다.
- 질의가 부정확하면 승인하지 않고 `rejected`와 이유를 기록한다. 질의 수정은 새 자식 질의 버전으로 검색/판정을 다시 생성하며, 구 결과는 보존한다.

### C4. 실제 검토 출처와 불일치 처리

- 검토 ID, query_id/doc_id, 각 내용 해시를 모두 대조한다. 해시만 맞고 ID가 다른 행은 거부한다.
- 검토 원본은 append-only 사본으로 보존한다. 판정 변경은 변경 이력과 새 판정 버전을 만든다.
- 두 사람이 검토하면 `review_item_id + reviewer_id`로 독립 기록을 보존하고 불일치를 별도 조정한다. 마지막 CSV 행으로 덮어쓰지 않는다.
- 1명만 가능하면 진행하되 `single_human_reviewer`와 예비 판정이라는 한계를 보고한다.
- AI 설명/판정 초안은 필요할 때 별도 machine 파일에만 저장하며 블라인드 사람 화면에 먼저 노출하지 않는다. AI 판정을 확정 지표나 사람 수에 포함하지 않는다.
- 프로그램은 파일 형식·출처 기재·내용 연결을 검사할 뿐 사람 신원을 인증했다고 주장하지 않는다.

사람 자료가 없으면 여기서 품질 점수를 확정하지 않는다. 그러나 Stage B의 수정/테스트, Stage E의 기계적 분석, Stage H의 검토 대기 보고/이미지/push는 계속한다.

## 6. Stage D — 부분 검토 채점과 보고 상태 보강

### D1. 공통 판정 풀의 동결과 완료 조건

질의별로 비교할 모든 방법·두 scope의 Top-5 합집합 및 추가 근거 문서를 `pool_version`으로 동결한다. ‘완료’는 **이 유한한 목록의 판정 완료**를 뜻한다. 전체 GitHub 또는 모든 corpus 문서를 판정하라는 뜻이 아니다.

- `query_approved`: 정보 충실성/누출/조건 계약이 실제 승인됨.
- `pool_complete`: 공통 목록의 각 문서가 해당 평가 범위에서 조정된 0/1/2 판정을 가짐.
- `pool_incomplete`: 미판정·자료 불충분·조정 대기가 남음.
- `execution_error`, `empty_corpus`, `no_lexical_match`는 서로 다른 상태로 유지.

새 방법이 새로운 문서를 상위에 올렸다면 그 문서를 기존 정답에서 자동 0점으로 보지 않는다. 공통 풀을 확장해 새 판정을 받고 **기존 방법도 같은 새 qrels 버전으로 다시 채점**한다. 풀 변화에 따른 점수 변화와 검색 순위 변화는 별도다.

### D2. Hit@5와 비교 분모

Hit@5는 Top-5에 직접 관련(grade=2) 문서가 하나 이상이면 1이다.

- 부분 검토 중에도 이미 확인한 직접 관련 문서가 있다면 `confirmed_hit=1`이라는 관찰을 남길 수 있다.
- 미판정이 남았고 직접 관련 문서가 확인되지 않았다고 0을 주지 않는다.
- 공식 방법 비교 표는 승인된 질의이면서 공통 풀 판정이 완료된 동일 질의 집합으로 계산한다. 방법마다 유리한 완료 질의만 택하지 않는다.
- 정상 빈 결과는 검토 완료 과제에서 Hit=0. 실행 오류는 순위 품질 값 null, 전체 시도 상태표에서는 실패로 유지한다.
- Bug 필터가 직접 관련 문서를 지웠어도 과제를 삭제하지 않는다.

모든 표에는 `계획 N / 질의 승인 N / 공통 풀 완료 N / 실행 오류 N / 실제 비교 N`과 제외 이유를 표시한다. 분모가 0이면 null이다. 검토가 덜 된 상태를 ‘성능 0%’로 표시하지 않는다.

기존 두 해석을 유지한다:
1. 검토 완료 과제 전체의 Hit@5: scope에서 관련 문서가 빠진 문제도 포함.
2. 해당 scope 안에 직접 관련 문서가 있다고 확인된 동일 질의의 조건부 Hit@5.

`scope에 알려진 직접 관련 문서 없음`은 풀 밖에도 아무 근거가 없다는 뜻이 아니다. 인증 무정답 검사와 구분한다.

### D3. pooled nDCG@5

- 이득: `2^grade - 1`, 할인: `log2(rank+1)`.
- 두 scope 비교는 동일한 C_raw 공통 판정 풀을 IDCG 분모로 사용한다.
- `query_approved && pool_complete`가 아니면 공식 pooled nDCG@5는 null.
- IDCG=0은 null과 사유. grade=1만으로 nDCG가 높아질 수 있음을 Hit@5와 함께 설명.
- 특정 시스템의 Top-5만 판정돼서 분모가 작아진 상황을 최종 nDCG=1로 보고하지 않는다.
- `unavailable`은 명시적인 미확정이지 0점이나 임의 풀 제외가 아니다. 해당 질의의 nDCG는 대기 상태로 둔다.

필수 회귀 테스트 예시(실제 실험 결과가 아닌 수식 fixture):

```text
결과: [A, B, C, D, E]
공통 풀: [A, B, C, D, E, F]
판정: A=2, B=C=D=E=0, F=null
=> confirmed_hit=1은 가능; pool_complete=false; 공식 nDCG=null

F=2가 실제로 판정됨
=> DCG=3; IDCG=3+3/log2(3); nDCG≈0.613147
```

### D4. 집계·완료 상태

- A/B/C, 저장소, 사례 유형, scope를 구분한다. 비교하는 행은 질의와 qrels 버전이 같아야 한다.
- 개선/동률/악화의 사례 ID와 n/N을 보고한다. 비율 차이는 퍼센트포인트, nDCG 차이는 점수 차이다.
- 번역·변형·반복 검색을 독립 표본으로 세지 않는다. 12개 개발 사례라는 한계를 유지한다.
- 작은 개발 표본에 p값·임의 성능 합격선·신규성 점수를 붙이지 않는다. 이 표본에서 고른 수정은 독립 최종 성능 검증이 아니다.
- 부분 완료와 전체 완료를 별도 표시한다. E1/E2/E3·수동 비교 완료 여부까지 하나의 `PILOT_EVALUATED`에 합쳐 숨기지 않는다.

### D5. 보고서 상태를 실제 자료에서 계산

- 사람 수·판정 수·평가 가능한 질의 수를 고정 숫자가 아닌 입력 파일에서 집계한다.
- 사람 qrels를 받은 경우에만 실제 grade·지표를 표시한다. 이전 `human_grade=None`, `UNJUDGED` 고정 출력을 후속 보고 경로에서 없앤다.
- 구 `run_001/report.md`는 그대로 남기고 새 report에 부모 링크와 변화 이유를 적는다.
- pending → partial → reviewed 전환이 파일·표·그림·설명에 일관되게 반영되는지 테스트한다.
- 새로운 score/report가 기존 rank를 바꿨다면 오류다. 같은 결과의 재채점인지, 새 검색인지 결과에 명시한다.

## 7. Stage E — 수정 전에 가능한 기계적 원인 감사

사람 검토 전에도 다음은 수행한다. 단, ‘관련성이 높다’는 판정은 하지 않는다.

### 감사 A_scope — 범위와 원문 연결

각 알려진 근거 문서에 `C_raw 포함 / C_bug 포함 / 실제 인덱스 포함 / 참고 원문 순위`를 연결한다. 참고 원문 하나가 빠졌어도 다른 직접 관련 문서가 반환될 수 있으므로 질의 전체 실패와 동일시하지 않는다.

이미 있는 두 scope 결과를 이용한다. 원문 레이블이나 최신 문서 범위를 몰래 바꿔 다시 실행하지 않는다.

### 감사 A_token — 한국어 기술 토큰 추적

`CMake로`, `MinGW로`, `Gemma4에서`, `generate를` 같은 기존 입력과 원문의 실제 기술 토큰을 현재 tokenizer로 확인한다.

각 사례에 다음을 저장한다:
- 원문 질의, 현재 추출 토큰, corpus에 존재하는 기술 토큰.
- 일치한 토큰/일치하지 않은 토큰. 한국어 기술어 누락 외에 다른 일치도 있는지.
- BM25 빈 결과인지, 공통 단어 하나만 매칭돼 다른 문서가 상위인지.

원문에 해당 토큰이 없거나 누락이 재현되지 않으면 그 사례를 ‘조사 분리 오류로 인한 실패’로 확정하지 않는다.

### 감사 A_rrf — RRF 기여분 재구성

RRF는 정확한 토큰 점수와 임베딩 점수를 직접 더하는 방식이 아니다. [S3]

특히 기존 O-E1처럼 의미 순위와 결합 순위가 다른 사례를 추적한다. 출력은 질의별·문서별:

`bm25_rank, semantic_rank, in_lexical_window, in_semantic_window, lexical_rrf_term, semantic_rrf_term, fused_score, fused_rank`.

- 상위 50개 바깥 후보에 기여분을 임의로 부여하지 않는다.
- 전체 순위가 없으면 고정 데이터로 생성하거나 `not_recorded_beyond_top20`으로 남긴다.
- 재구성 점수와 저장 점수가 맞는지 검산한다.
- 두 검색에서 보통 순위인 문서가 한쪽에서만 높은 문서보다 올라오는 경우를 표로 보여 준다. 그것이 실제 관련성을 해쳤는지는 사람 판정과 분리한다.

### 감사 A_chunk — 최대 유사도 구간 추적

기존 로컬 `runs.jsonl`의 구간 진단 자료를 확인한다. 실제 최대 점수를 만든 질의/문서 구간, 토큰 수, 구간 수를 연결한다. 공개 자료에는 필요한 짧은 구간만 마스킹 후 내보낸다.

사람이 증상/환경/템플릿/관련 기능/미확인으로 구분한 후 원인 설명에 연결한다. 문서 길이가 길다는 이유만으로 원인이라고 하지 않는다. 전체 평균·짧은 문서 우대 등 새 검색 규칙은 이번에 넣지 않는다.

## 8. Stage F — 사람 근거가 있는 실패만 단일 변경 비교

아래 전체는 **[추정·미검증] 제한된 개발 진단**이다. 기존 표준의 입력 분석/순위 결합 설정을 시험하는 것이며 새 연구 방법이나 효과를 주장하지 않는다. 설정은 새 순위를 보기 전에 파일로 동결한다.

### F0. 실행 게이트

- 실제 사람의 질의 승인, 직접 관련/경쟁 문서 근거가 있어야 한다.
- 필요한 원문·모델·기준선 재현이 확인되어야 한다.
- `gate_reason`, `evidence_ids`, 적용 사례와 제외 이유를 남긴다.
- gate를 못 넘으면 원인 진단/후속 준비까지 완료하고 `DEFERRED_NO_VALIDATED_FAILURE`로 표시한다.
- 통과했다면 아래 명시한 범위는 추가 승인 없이 실행 가능하다. 한 요소씩 변경하며 운영 기본값은 바꾸지 않는다.

### F1. K1 — 한국어에 붙은 기술 토큰의 질의측 보존

**해결하려는 것:** 한국어와 붙은 영문 기술 식별자가 정확히 매칭되지 않는 문제.

**단순 대안:** 원래 BM25와 의미 검색을 그대로 사용하거나 사용자가 띄어 쓰는 것. 새 형태소 모델을 먼저 설치하지 않는다.

**신규 제안 규칙 `query_ascii_boundary_v1`:**
- 기존 질의 토큰을 유지한다.
- 한글과 영문이 섞인 토큰에서 라틴 문자를 포함한 연속 기술 식별자 부분을 추가 추출한다.
- 예: `CMake로`→기존 토큰+`cmake`; `Gemma4에서`→기존 토큰+`gemma4`; `generate를`→기존 토큰+`generate`.
- 점·밑줄·버전·연결 기호를 다루는 구체적 규칙을 테스트와 설정에 동결한다. 순수 숫자 조각을 새로 확장하지 않는다.
- 이미 있는 토큰을 다시 더해 가중치를 의도치 않게 높이지 않는다. 순수 영문 질의와 띄어 쓴 기술어는 기존 출력이 유지되어야 한다.
- 원래 한국어 문장/오류 문구를 삭제하지 않는다. 문서측 tokenizer·BM25 통계·의미 검색·RRF 설정은 바꾸지 않는다.

이 휴리스틱 자체의 성능은 미검증이다. scikit-learn 문서는 tokenizer/analyzer를 분리해 다루는 일반 원리를 뒷받침할 뿐 이 규칙의 유효성을 증명하지 않는다. [S4]

비교:
1. 기존 BM25 vs K1 BM25.
2. 기존 Hybrid vs **K1 BM25 + 기존 의미 검색 + 기존 RRF**.

같은 36질의·2scope에서 평가용 결과를 생성하되, 승인/판정 완료 집합의 공식 점수만 공개한다. 최대 144개 새 논리적 검색 조건이다. baseline은 검증된 저장 결과를 재사용할 수 있다.

새 후보의 Top-5 문서를 공통 판정 풀에 추가하고 방법/점수를 가린 추가 검토를 받은 뒤 모든 방법을 같은 새 풀로 재채점한다. 원문 순위만 올랐다고 성공으로 채택하지 않는다.

### F2. R1 — RRF의 Top-50 절단 영향만 검사

**해결하려는 것:** 한쪽에서 유용하게 찾은 문서가 다른 검색의 Top-50 밖이어서 결합 기여를 잃는지 확인.

**신규 실험 `rrf_full_window_probe`:**
- 기존 tokenizer, corpus, BM25, 임베딩, RRF 상수 60, 동일 가중치를 유지한다.
- 결합 창만 50에서 **그 고정 corpus에서 실제 생성한 각 전체 순위 길이**로 바꾼다.
- BM25에서 실제 무일치로 제외된 문서에 순위를 만들어 넣지 않는다.
- 비교는 기존 semantic, 기존 RRF(50), RRF(전체 창). K1과 조합하지 않는다.
- 정답을 봐서 창 크기 100/200/300 중 좋은 값을 고르는 탐색을 하지 않는다.

RRF의 window와 개별 기여분은 표준 구현에서 구분되는 설정이다. [S3] 창을 늘리면 반드시 좋아진다는 뜻이 아니며, 절단을 없애도 두 목록에 같이 등장하는 문서가 유리할 수 있다. 결과가 나쁘거나 같으면 그대로 보고한다.

36질의 × 2scope = 최대 72개 새 결합 결과. 구 Top-20 출력만으로 전체 창을 계산할 수 없으므로 필요시 기준선 전체 순위를 최대 72조건에서 재생성한다. 실제 재추론/캐시 재사용을 구분한다.

이 비교는 원인 분해용이다. 개선돼도 새로운 독립 사례의 검증 없이 운영 기본값으로 자동 승격하지 않는다.

### F3. 필터 범위 — 새 규칙보다 기존 결과를 판정

기존 C_raw/C_bug 순위와 사람 qrels를 이용해 다음을 분리한다:
- 유용한 문서가 필터에서 제외돼 잃은 것.
- 덜 관련된 후보가 줄어 순위가 좋아진 것.
- 문서 삭제뿐 아니라 BM25의 문서 빈도/길이 통계도 scope에 따라 달라질 수 있다는 점.

문서 문제·사용법 문제까지 서비스 대상인지의 범위 질문을 남긴다. `bug`를 임의의 추가 레이블로 바꿔 점수를 맞추거나, 세 수정(K1/R1/필터)을 한꺼번에 적용하지 않는다.

### F4. 판정

각 변경은 `유지 / 조건부 유지 / 보류 / 기각`으로 보고한다. 근거는 동일 질의의 직접 관련성, 순위, 정보 조건, 부작용, 비용이다. 개발 표본에서 개선 여부와 채택 여부는 구분한다. 현재 표본을 무작위 분할해 새로운 test라고 부르지 않는다.

## 9. Stage G — 미완료 행동 검사와 기존 검색 비교

기존 프로토콜의 실험 식별자 E1/E2/E3를 유지한다. 앞 절의 기계적 감사 A_scope/A_token/A_rrf/A_chunk와 구분해 결과에는 `protocol_experiment=E1` 등을 명시한다. 새 기능을 준비했다고 실행 완료로 보고하지 않는다.

### G1. E1 표현 유지·무관 정보 추가

- 기존 `evaluation/scenario_pilot_v1/E1-variants.draft.json`과 검토 양식을 실제 읽고 재사용한다.
- 원래 선정된 4사례의 B에 표현 바꾸기/무관 정보 소량 추가를 적용한다.
- 실제 사람이 의미 동등성을 승인한 변형만 확정 행동 검사로 실행한다.
- `4사례 × 2변형 × 기존 3방법 × 2scope = 최대 48회`.
- 중요한 오류 코드·버전·단위·조건을 무관 정보로 지우지 않는다. 개인정보는 합성 값만 사용한다.
- 동등성이 확인돼도 새 Top-5의 미판정 문서는 추가 검토한다. 동일 정보가 유지될 때의 유용한 결과 소실/회복을 본다. 전체 순위 일치를 강제하지 않는다.

### G2. E2 조건 대조

- 저장소별 최대 1쌍, 총 2쌍. 원래 corpus 안의 실제 본문 근거로 질의별 관련 문서/중요 조건을 확인한다.
- 각 문서의 관련성은 질의별로 판단한다. 조건을 바꿨다는 이유만으로 무조건 순위가 뒤집혀야 한다고 가정하지 않는다.
- `2쌍 × 2질의 × 기존 3방법 × 2scope = 최대 24회`.
- 양쪽 상황의 근거가 없으면 `BLOCKED_CONDITION_EVIDENCE`로 표시하고 억지 사례를 만들지 않는다.

### G3. E3 작은 집합 무정답

- 저장소별 1질의, 각 최대 20문서의 작은 통제 집합.
- 사람이 집합 전체를 검토한 뒤 모든 grade=2 문서를 제거한 minus 집합과 plus 집합을 비교한다.
- minus에 2점 또는 미판정이 있으면 무정답으로 인증하지 않는다. 빈 집합만 남는 검사는 유의미한 무정답 스트레스 검사로 주장하지 않는다.
- `2질의 × plus/minus × 기존 3방법 = 최대 12회`.
- Hit/순위 품질은 plus에서 보고한다. minus에서 관련 문서를 못 찾은 사실은 당연한 조건이므로 검색기 실패율로 합산하지 않는다.
- minus에서는 반환 후보·점수·화면 설명이 어떠한지 기록한다. 후보를 반환한 것 자체를 오류로 판정하거나, 아직 없는 거절 기능을 구현된 것처럼 평가하지 않는다.
- ‘해당 작은 문서 집합에 직접 관련 문서 없음’이지 GitHub 전체에 없음이 아니다.

### G4. 기존 웹 검색·GitHub 검색·앱 수동 비교

기존 `manual_web_study.template.csv`를 기반으로 한다. 현재 사람이 기록한 사용 자료가 없다면 자동으로 사용자 시간/성공을 만들지 않는다.

- 같은 정보 요구·오류·환경을 제공한다. 웹 검색은 키워드만 쓰는 시스템이라고 가정하지 않는다.
- 같은 사람이 같은 문제의 답을 반복해 보지 않도록 참가자/문제/도구 순서를 교차 배정한다. 이미 정답을 본 사람은 exposure를 기록한다.
- 검색어 수정과 문서 읽는 시간을 포함한다. 외부 사이트의 유용한 근거도 일반 검색의 성공으로 인정한다.
- 새 운영 상한 [추정]: 과제당 5분을 동일하게 적용하는 소형 파일럿으로 시작할 수 있다. 실제 시작 전에 참가자가 한도와 기록법을 확인한다. 이는 유용성 합격선이 아니다. 다른 한도를 쓰면 모든 도구에 동일하게 사전 기록한다.
- 직접 관련 근거 발견 여부, 근거 URL, 조건 판단, 시작/종료, 제한 도달, 열람 문서 수, 실제 질의를 저장한다. 실패/시간 제한 도달은 평균에서 삭제하지 않는다.
- 참가자가 없으면 `PENDING_MANUAL_STUDY`. CLI의 기계적 검색 결과와 사람 사용성 자료를 섞지 않는다.

### G5. 요약

현재 요약 미구현이면 `NOT_APPLICABLE_YET`와 이유를 유지한다. 이 지시로 요약 API를 추가하거나 요약 품질 실험을 수행하지 않는다.

- 지시문 범위 밖의 대형 수집·새 모델·여러 가중치 탐색은 변경안으로 보고하고 자동 실행하지 않는다.

## 11. 필수 자동 테스트 — 테스트 수 자체를 목표로 하지 말기

실제 source에서 재사용 가능한 fixture와 함수를 먼저 찾아라. 새로운 정확도 레이블을 테스트 fixture에서 실험 정답으로 옮기지 않는다.

1. 구 run 파일을 읽고 새 채점/보고를 수행해도 부모 파일 해시가 변하지 않는다.
2. 새 scorer/reporter 변경이 부모 retrieval 해시를 몰래 덮어쓰지 않으며 입력 변경은 검출된다.
3. review_item_id, query_id, doc_id, 내용 해시의 불일치 행을 거부한다.
4. 승인되지 않은 질의/기계 판정/누락된 실제 검토 출처를 사람 qrels로 사용하지 않는다.
5. 복수 검토자 판정을 덮어쓰지 않으며 불일치 미조정은 null이다.
6. Top-5 밖 공통 풀의 미판정이 남으면 공식 nDCG는 null이다. F 문서 fixture 계산을 독립 검산한다.
7. IDCG=0, grade=1만 있는 경우, 정상 빈 결과, 실행 오류, 미판정을 서로 다르게 처리한다.
8. 방법 비교의 질의 목록과 qrels 버전이 같고, 필터로 빠진 과제가 사라지지 않는다.
9. 새 후보 문서 때문에 풀이 확장되면 baseline 포함 전 방법을 같은 새 풀로 다시 채점한다.
10. 역사 사례·번역·변형·시간 반복을 독립 핵심 사례로 세지 않는다.
11. pending/partial/reviewed 상태 변화가 보고서·JSON·그림의 수치와 일치한다.
12. K1 gate를 충족해 구현했다면 혼합 기술 토큰, 순수 영어 무변경, 중복 토큰 방지, 숫자/기호 보존을 확인한다.
13. R1을 구현했다면 원래 RRF50 그대로 재현, 절단에 따른 기여분 0, 전체 창 계산, 무일치 문서 비삽입을 확인한다.
14. E1/E2/E3는 필요한 사람 승인/완전 판정이 없으면 확정 채점이 되지 않는다.
15. HTML/CSV/MD에 외부 스크립트나 스프레드시트 수식이 의도치 않게 실행되지 않게 export를 안전하게 처리한다. 원본 검색 입력 자체를 몰래 변경하지 않는다.
16. 공개 파일의 내부 상대 링크와 PNG 경로가 실제 존재한다. report의 수치와 집계 원본이 일치한다.
17. 원본에 없는 실패 원인·버전·해결책을 report가 하드코딩하지 않는다.

기존 테스트를 먼저 실행하고, 마지막에는 **실제 게시할 코드 트리**를 분리해 테스트한다. 로컬에서만 존재하는 다른 변경을 포함한 통과 수와 게시 코드의 통과 수를 혼동하지 않는다.

### H1. 공개 폴더와 자료 구성

다음은 신규 제안 구조다. 같은 역할의 자료가 있으면 재사용하고 최종 경로를 README에 명시한다.

### H2. 공개 근거와 개인정보

- 검토자가 ‘무슨 입력에 무엇이 나왔는지’를 읽을 수 있도록 질의, 실제 제목/번호/URL, 상위 순위, 판정 상태, 필요한 짧은 근거를 제공한다.
- 기존 원문 전체·사용자 객체·이메일·토큰·개인 절대경로·모델/벡터 전체는 기본 공개하지 않는다.
- 필요한 인용만 최소한으로 공개하고 동일 원문 인용은 evidence ID로 재사용한다. 학습 데이터/전체 Issue 덤프의 이용권을 임의로 주장하지 않는다.
- 민감정보 마스킹은 공개 복사본에만 적용한다. 검색에 사용한 원본 해시와 공개 복사본 해시를 구분하고 변형 여부를 기록한다.
- 근거 자체가 마스킹으로 사라지면 검증 가능한 공개 증거라고 주장하지 않는다. `restricted_evidence`와 원본 보존 위치 유형을 기록한다.
- 검토자 이름 대신 본인이 정한 가명을 공개할 수 있다. 프로그램이 가짜 사람 검토자를 만들면 안 된다.
- 공개 MD/PNG는 사람 검토를 위한 블라인드 원본과 분리한다. 결과 순위가 보이는 casebook을 새 검토자에게 블라인드 자료라고 전달하지 않는다.

정확한 원본 재실행이 로컬 스냅샷을 요구한다면 명시한다. 공개 자료로 가능한 것은 **수치 재집계/보고 감사/선별 근거 확인**이고, 모든 원문 임베딩의 완전 재현과는 다르다.

## 13. Stage I — 안전하게 커밋·push하고 원격 확인

사용자는 이번 작업의 GitHub push를 명시적으로 승인했다. 이전 프로토콜의 push 금지는 **이번 작업 범위의 공개 게시**에 한해 대체한다. 이것은 무관한 파일·비밀정보 게시, main 강제 변경, 자동 배포 승인이 아니다.

### 게시 절차

1. 원격 저장소를 다시 확인하고 변경 파일의 allowlist를 만든다.
2. 원본 실험/사용자 미커밋 파일이 달라지지 않았는지 해시·git diff로 확인한다.
3. 신규 평가·검토 도구·테스트·보고·소형 원자료·PNG만 파일 경로별로 staging한다.
4. 민감정보·대형 파일·깨진 링크·null 오표시·테스트 로그의 실행 트리를 검사한다.
5. **실제 게시될 소스 트리**를 별도 위치에서 테스트한다. 무관한 미커밋 파일이 테스트 결과를 좋게 만들지 않게 한다. 게시 대상 식별과 실제 명령/exit code를 기록한다.
6. 사용자 지정 브랜치가 없으면 `eval/scenario-followup-v2-20261001` 같은 새 브랜치에 커밋·push한다. 충돌하면 새 suffix를 쓰고 최종 이름을 보고한다. main 자동 병합·force push는 하지 않는다.
7. 가능한 경우 상태와 소형 결과가 먼저 완성되면 검토 대기 단계에서도 push한다. 미완료를 완료로 표시하지 않고 같은 브랜치에 이후 검토 결과를 별도 커밋으로 게시할 수 있다.
8. push 후 `git ls-remote` 등으로 원격 브랜치 HEAD와 실제 커밋을 확인한다. 원격 diff 파일 목록이 allowlist와 맞는지도 확인한다.
9. commit 고정 URL로 README/report·대표 CSV/JSON·PNG를 실제 fetch해 해시/파일 존재/내용을 확인한다. 원격 이미지가 정상 이미지로 열리는지 확인한다.
10. 권한/브랜치 보호/인증 문제로 실패하면 우회하지 말고 `PUSH_FAILED`로 기록하고 로컬 완료 상태·실제 실패 원인·재개 명령을 보고한다.

마지막 커밋 SHA를 그 커밋 안의 파일에 무한히 다시 쓰는 순환을 만들지 않는다. 파일에는 run/source-tree 식별자를 쓰고 최종 원격 commit URL은 CLI의 사용자 보고와 별도 로컬 publication receipt에 기록한다. 필요하면 후속 메타데이터 커밋이 어느 커밋을 검증하는지 명시한다.

루트 주소만 주면 다음 검토자가 main의 구 결과를 볼 수 있다. **최종 응답에는 새 브랜치와 commit 고정 보고서 URL을 반드시 제공한다.**

## 14. 실행 인터페이스와 중단 후 재개

아래 명령 이름은 **신규 제안 인터페이스**이며 현재 구현된 명령이 아니다. CLI는 같은 기능의 기존 경로를 재사용하거나 작은 wrapper를 구현하고, `--help`와 실제 소규모 실행으로 검증한 최종 명령을 README/사용자에게 제공한다.

```text
python -m evaluation.scenario_followup audit --parent-run <확인한_원본> --out <새_batch>
python -m evaluation.scenario_followup prepare-review --batch <새_batch>
python -m evaluation.scenario_followup resume --batch <새_batch> --query-reviews <실제파일> --reviews <실제파일>
python -m evaluation.scenario_followup report --batch <새_batch>
python -m evaluation.scenario_followup verify-publication --batch <새_batch>
```

`resume`는 자료 상태에 따라 다음을 수행한다:
- 검토 없는 경우: 감사/검토 패키지/대기 보고만 완료.
- 일부 검토: 같은 완료 질의 집합의 부분 점수, 남은 검토 목록 생성.
- 검토 완료 및 실패 게이트 충족: 해당 단일 변경과 승인된 행동 검사 실행, 새 후보 풀 생성.
- 새 후보가 미판정: 새 결과는 순위 관찰로만 게시하고 추가 검토 대기.
- 공통 풀 재검토 완료: baseline과 수정안을 동일 qrels로 채점, 결과·그림·한계 보고.

기존 결과를 재실행/재작성하지 않도록 단계별 입력 해시와 output 존재를 검사한다. 이미 같은 입력으로 완료된 단계는 명시적으로 재사용한다. 오래된 qrels나 다른 질의 파일을 제공하면 오류로 거부한다.

### 표준 원리 — 새 구현의 효과 보장은 아님

- S1. Introduction to Information Retrieval(2008/Cambridge University Press), Assessing relevance. 여러 검색기의 후보 풀과 사람 판정, 판정자 간 차이를 설명한다. 이번 pool 완료·부분 보고 정책은 프로젝트용 보강 설계다.
  https://nlp.stanford.edu/IR-book/html/htmledition/assessing-relevance-1.html
- S2. Beyond Accuracy: Behavioral Testing of NLP Models with CheckList(2020/ACL). 불변 정보/중요 조건 변경 같은 행동 검사 원리. 이 프로젝트의 구체적 변형과 무정답 사례의 타당성은 별도 검토가 필요하다.
  https://aclanthology.org/2020.acl-main.442/
- S3. Elasticsearch 공식 문서, Reciprocal rank fusion. RRF 공식, 순위 창, 개별 기여분 설명. 전체 창 후보의 개선을 보장하는 인용으로 사용하지 않는다.
  https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion
- S4. scikit-learn 공식 문서, Feature extraction / Customizing the vectorizer classes. 입력 분석과 tokenization 사용자 정의의 일반 원리. 한국어 혼합 토큰 보존 휴리스틱의 품질은 이번에 검증한다.
  https://scikit-learn.org/stable/modules/feature_extraction.html#customizing-the-vectorizer-classes

최종 원칙: **원본을 보존하고 → 실제 판정을 연결하고 → 실패 하나씩 비교하고 → 근거·수치·PNG를 원격에 게시해서 검토할 수 있게 한다.** 사람이 아직 판단하지 않은 부분은 숨기지 않되, 그 이유로 자동으로 가능한 준비와 공개까지 미루지 않는다.
